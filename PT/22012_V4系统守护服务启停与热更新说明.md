## 六、哪些改动可以热重载

以下改动通常不需要停止系统守护进程：

- 修改 8093 的 HTML、CSS、前端 JS 片段，并且代理服务每次 HTTP 请求都从磁盘重新读取文件。
- 修改纯静态资源，如 logo、图片、CSS 覆盖文件、前端内联样式。
- 修改数据库里的业务数据、知识库内容、RAG chunk，后端每次查询时重新读取数据库。
- 只做浏览器内存覆盖验证，例如 Playwright route fulfill 临时替换 HTML；浏览器关闭后自动失效。

这些场景下，常用验证方式是刷新页面或加 cache-bust 参数：

```text
http://10.30.220.12:8093/?t=manual-check-20260714#overview
```

能热生效的原因是：浏览器拿到的是新静态文件，或者后端下一次查询会读到新数据库内容；原来的 Python 进程不需要重新导入模块，也不需要重新读取环境变量。

## 七、哪些改动必须停守护并重启

以下改动必须停止对应系统守护进程，修改后再启动或重启：

- 改 `service_configs/*.json` 中的 `arguments`、`env`、端口、工作目录、Python 入口。
- 改 `BF_LLM_MODEL`、`OLLAMA_BASE_URL`、`BF_PUBLIC_MODEL_NAME` 这类模型供应参数。
- 改 Python 后端代码，并且该模块在服务启动时已经 import 到进程内。
- 改 WebSocket 桥接、Chronos 服务、Ollama 服务这类常驻进程入口或环境变量。
- 改端口绑定、数据库连接 profile、MCP 数据源、SDK 路径等只在启动时读取的配置。
- 清理或切换大模型 runner、显存占用、`OLLAMA_MAX_LOADED_MODELS`、`OLLAMA_KEEP_ALIVE` 等 Ollama 运行参数。

必须重启的原因是：这些值在进程启动时已经被读取成环境变量、全局常量、命令行参数或已导入模块；浏览器刷新只能重新请求页面，不能让服务器进程重新读取这些启动参数。

## 八、刚才 8093 模型切换为什么必须停守护

8093 的模型供应链路是：

```text
BFV4PreviewProxy8093 服务
-> manage/run managed service
-> start_v3_8092_python.py --port 8093 --model <底层模型>
-> 设置 BF_LLM_MODEL 环境变量
-> 启动 ollama_proxy_server.py
-> ollama_proxy_server.py 启动时读取 DEFAULT_MODEL
-> 调用 http://127.0.0.1:11434/api/chat
```

本次第一次切换没有立即成功，原因有两个：

- `env.BF_LLM_MODEL` 已经改成 `chiqiong-blast-furnace:latest`，但 `arguments` 里仍然写着 `--model bf-diagnosis-runtime:v1`，启动脚本用命令行参数覆盖了环境变量。
- 普通 `Restart-Service` 没有完全清掉旧的 8093 Python 子进程，旧进程仍占用 8093 并继续返回旧模型状态。

最终修复方式是同时更新：

- `22012_BFV4PreviewProxy8093.json` 的 `arguments`：`--model chiqiong-blast-furnace:latest`
- `22012_BFV4PreviewProxy8093.json` 的 `env.BF_LLM_MODEL`：`chiqiong-blast-furnace:latest`
- 停止 `BFV4PreviewProxy8093`
- 只清理命令行含 `V4_8093_PREVIEW` 的 8093 旧监听进程
- 再启动 `BFV4PreviewProxy8093`

当前验收口径：

```text
/api/ollama/status: ok=true, model_ok=true, target_model=炽穹·高炉炼铁大模型
父进程命令行: --model chiqiong-blast-furnace:latest --public-model 炽穹·高炉炼铁大模型 --port 8093
```

注意：`target_model=炽穹·高炉炼铁大模型` 是公开显示名，不是底层 Ollama 标签。底层模型以父进程 `--model chiqiong-blast-furnace:latest`、配置文件 `arguments/env.BF_LLM_MODEL` 和 `model_ok=true` 共同确认。

## 十一、问答慢的守护相关排查

8093 问答慢时，不要只看 `/api/ollama/status` 是否 `model_ok=true`。该接口只能说明代理和目标模型可用，不能说明整条问答链路没有换模或检索等待。

2026-07-14 已核查到一个关键慢点：8093 的知识库检索会调用 `nomic-embed-text` 做 embedding，而旧 Ollama 守护配置 `OLLAMA_MAX_LOADED_MODELS=1` 会导致每轮问答准备阶段可能先加载 embedding 模型并换出 27B，随后真正回答时再重新加载 `chiqiong-blast-furnace:latest`。实测 embedding 后重新预热 27B 约 `55s`。

**2026-07-14 历史方案**：当时曾将 `BFOllama11434` 的 `OLLAMA_MAX_LOADED_MODELS` 调整为 `2`，目标是让 27B 主问答模型与 `nomic-embed-text` embedding 小模型同时驻留；该方案的性能数据仅用于历史对照，已由 2026-07-26 单 27B 策略取代。

同日已同步 8093 问答代理优化：状态/数据类问题会按意图跳过不必要的知识库 embedding；流式接口会先发送 `start(stage=preparing)`，避免前端 10 秒级空等。**现行重建规则相反**：必须保持 `OLLAMA_MAX_LOADED_MODELS=1`，8094 使用 keyword 检索；若要恢复向量检索，应把 embedding 迁到独立端口或独立运行时，不得恢复 11434 双驻留。

## 十二、8093 问答性能参数与重启边界

2026-07-14 起，8093 后端启用可选 PostgreSQL 小型连接池，并把助手库、RAG 和 pgvector schema 检查移到进程启动阶段。远端 `C:\Program Files\Python311\python.exe` 已安装 `psycopg-pool==3.3.1`。连接池相关环境变量为：

```text
BF_ASSISTANT_PG_POOL_ENABLED=1
BF_ASSISTANT_PG_POOL_MIN_SIZE=1
BF_ASSISTANT_PG_POOL_MAX_SIZE=6
BF_ASSISTANT_PG_POOL_TIMEOUT=10
```

修改这些变量、Python 后端、数据库连接参数、模型标签或 RAG 初始化逻辑后，必须重启 `BFV4PreviewProxy8093` 才会生效；只修改静态 HTML/CSS/JS 时仍可热更新，无需停止守护服务。只重启 8093 时不要停止 `BFV4PreviewWs8768`。

当前性能优化的时效边界：

- 每轮问答都重新读取当前传感器值和最新诊断，不缓存当前炉况。
- 不缓存最终答案，不会因重复提问而直接返回旧炉况内容。
- 8 小时趋势只在最新诊断时间与记录版本完全一致时复用，版本变化立即重新查询。
- 不缓存 embedding 或知识检索包，知识库仍按原检索参数实时取证。
- 数据预取包含完整变量、数值和时间时才跳过重复工具轮；图表、报表、比较和不完整预取仍执行工具。

修改后建议使用以下顺序验收：

验收时同时确认 8093 `model_ok=true`、8768 可达，以及 `/api/ps` 中 `chiqiong-blast-furnace:latest` 与 `nomic-embed-text:latest` 同时存在。
