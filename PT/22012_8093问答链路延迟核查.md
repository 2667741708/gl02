## 一、结论

8093 当前慢点不主要在 27B 模型本身生成。

已确认 27B `chiqiong-blast-furnace:latest` 热驻留时，直连 Ollama 流式首 token 约 `1.0s`，总耗时约 `1.2s`。前端问答仍慢，主要来自 8093 问答代理在真正开始可见回复前执行了上下文准备、数据库预取、知识库 RAG 检索和可能的 MCP 工具轮。

其中最关键的实测原因是：

- 8093 知识库检索会调用 embedding 模型 `nomic-embed-text`。
- 旧 Ollama 守护配置为 `OLLAMA_MAX_LOADED_MODELS=1` 时，一次 RAG embedding 调用可能把 27B 从显存/runner 中换出。
- **2026-07-14 历史状态**：当时曾将 `OLLAMA_MAX_LOADED_MODELS` 调整为 `2`，允许 27B 主问答模型与 `nomic-embed-text` embedding 小模型同时驻留；现行值已收敛为 `1`。
- 因此 RAG 检索阶段调用 embedding 后，27B 仍可保持常驻，避免随后正式回答时重新加载 27B，从而降低首 token 延迟。

## 二、当前链路

```text
前端发送问题
-> 8093 /api/qa/chat
-> handle_qa_chat_stream()
-> prepare_qa_chat()
   -> 读取会话与当前快照
   -> 读取趋势/诊断上下文
   -> qa_mcp_prefetch(question)
   -> qa_search_knowledge(question)
      -> nomic-embed-text /api/embed
      -> pgvector/keyword/hybrid 检索
   -> 构造隐藏上下文 prompt
-> 如启用工具：run_qa_mcp_tool_loop()
-> 27B /api/chat stream
-> 前端开始出现 token
```

注意：当前 `handle_qa_chat_stream()` 是先执行 `prepare_qa_chat()`，再发送 SSE headers/start 事件。因此前端在上下文准备阶段会看到“还没有任何回复”的空等。

## 五、建议修复顺序

### 已执行修复 1：允许 27B 与 embedding 小模型同时常驻

`22012_BFOllama11434.json` 已从：

```text
OLLAMA_MAX_LOADED_MODELS=1
```

调整为：

```text
OLLAMA_MAX_LOADED_MODELS=2
```

调整后需重启 `BFOllama11434` 并预热 27B。理由：27B 约占 `23.9GB` 显存，`nomic-embed-text` 是小 embedding 模型，220.12 GPU 显存约 `46GB`，两者同时驻留比每轮换模更稳定。

注意：调成 2 后要避免同时加载另一个 20GB 级大模型。健康检查已改为 27B，不应再主动常驻旧 `bf-diagnosis-runtime:v1`。

### 优先修复 2：把 SSE start 提前发出

当前 SSE 的 start 事件在 `prepare_qa_chat()` 之后才发，用户会看到 10 秒以上空白等待。建议改成：

```text
收到请求 -> 立即发送 start/preparing 事件 -> 再做快照、检索、工具准备 -> 最后流式输出 token
```

这不能减少全部计算时间，但能显著改善前端体感，至少让用户知道系统正在“取数/检索/思考”。

### 优先修复 3：按意图减少不必要的 RAG 与工具轮

对“打招呼、简单问状态、无需知识库”的问题，不应每次都跑 `qa_search_knowledge()`。对“当前 P_top 最新值”这类问题，若 `qa_mcp_prefetch()` 已经拿到确定性数据，可以优先给出快速回答，避免再走完整模型工具轮。

本轮不切换模型、不降低量化精度、不减少输出上限，使用同一 27B 模型、同一 PostgreSQL 数据源和同一问题做分段与 A/B 测试。测量脚本已增加 SSE 事件时间线、`qa_prepare_timing_ms`、数据预取 A/B 和知识问答用例：

### 1. 分段结果

| 场景 | 准备阶段 | 首 token | 完成 | 结论 |
|---|---:|---:|---:|---|
| 直连 27B 简单问题 | - | `0.35s` | `0.72s` | 模型本体不是主要瓶颈 |
| 8093 简单问题 | DB `4.85-5.05s` | `7.14-10.96s` | `9.13-12.49s` | 固定数据库上下文准备占比最高 |
| 数据查询，默认重复工具轮 | DB `4.93s` + 预取 `0.02s` | `13.68s` | `14.01s` | 预取已命中后仍再次调用工具 |
| 数据查询，仅预取 + 27B 最终回答 | DB `4.85s` + 预取 `0.02s` | `7.14s` | `14.97s` | 首 token 降低 `6.54s`；完成时间较长是因为回答内容更长，不是推理变慢 |
| 知识问题，首次/热态 | DB `4.97-5.06s` + 检索 `4.21-5.68s` | `14.38-14.60s` | `23.54-23.79s` | RAG 初始化/embedding/检索仍是第二个大瓶颈 |

数据查询 A/B 两组都返回了相同的 `P_top` 最新值和数据时间，且都由 27B 生成最终现场解释；关闭的是已经被预取结果覆盖的重复工具选择与重复查询，不是关闭数据库事实核验。A/B 中“仅预取”回答更完整，说明该优化不需要用缩短答案换首 token。

### 2. 已定位的无降质优化点

1. **数据库和 RAG schema 只在进程启动时初始化一次。** 当前 `assistant_pg.db_connect()` 每次连接都会执行 `ensure_assistant_schema()`；代理层 `db_connect()` 又执行一次 schema 检查并重复 upsert 报表模板；RAG 每次检索还会执行 `ensure_rag_schema()` 和 `ensure_pgvector_schema()`。这些 DDL/目录检查不参与答案内容，应移到服务启动或显式迁移入口。
2. **最新快照和 8 小时趋势复用同一 PostgreSQL 连接。** 当前 `latest_pg_snapshot_for_qa()` 与 `recent_pg_diagnosis_snapshots_for_qa()` 串行各开一次连接。合并到同一只读事务可减少连接与往返，同时保证两部分数据来自同一时间截面，质量不会下降。
3. **按最新 `diagnosis_ts` 精确缓存 8 小时趋势。** 缓存键使用最新诊断时间、窗口和条数；时间戳不变时复用完全相同的趋势包，时间戳变化立即失效。不要只用长 TTL，以免引入不可见陈旧数据。
4. **预取完整命中时跳过重复 MCP 工具轮。** 仅当 `mcp_prefetch.used=true` 且结果包含所需变量、数值、时间窗/时间戳时跳过；画图、报表、多变量联查、预取失败或字段不完整时继续启用工具。实测可把数据问题首 token 从 `13.68s` 降到 `7.14s`。
5. **缓存完全相同查询的 embedding 与检索包。** 缓存键包含规范化问题、embedding 模型、检索模式、`top_k` 和知识库版本/内容哈希；命中时复用相同 768 维向量和相同证据，不改变召回质量。直连 embedding 连续三次为 `4486ms / 220ms / 196ms`，说明热态与重复计算有明显优化空间。
6. **为 PostgreSQL 使用小型连接池。** 8093 的助手库、生产快照和 RAG 都访问同一 PostgreSQL，复用健康连接可减少每轮握手；SQL、事务隔离与返回数据保持不变。
7. **减少 SSE 中重复的大列表传输。** `start(stage=prepared)` 和 `final` 不必每次都携带完整会话列表；可只返回当前会话并让前端异步刷新列表。这不影响回答内容，主要降低 VPN 下的序列化和传输开销。

### 3. 实施优先级与边界

建议先实施 `1 + 2 + 4`，它们不改变知识证据、炉况窗口、模型或回答上限，预期对简单/数据问题的首 token 改善最大。随后实施 `3 + 5 + 6`，并用固定问题集对比数值、时间、证据 `chunk_id` 和答案要点。

暂不把“缩短 8 小时窗口、降低 `top_k`、换小模型、降低量化精度、减少输出 token”列为首选，因为这些做法可能直接改变证据覆盖或回答完整度。意图化精简提示词可以继续研究，但必须先建立答案回归集后再启用。

## 九、2026-07-14 无降质优化实施与最终复测

本轮按用户确认范围实施数据库连接与初始化复用、最新值 SQL 优化、诊断趋势精确复用、完整预取后跳过重复工具轮、SSE 传输精简和分段计时。明确没有启用“相同问题直接复用旧答案”或 embedding/检索结果缓存，也没有缓存当前炉况最新值，避免时效性问题命中过时内容。

### 1. 已实施内容

- `assistant_pg.py` 使用可选的小型 `psycopg_pool` 连接池；远端 Python 3.11 已安装 `psycopg-pool==3.3.1`。依赖不可用时自动退回普通连接。
- 助手库 schema、报表模板和 RAG/pgvector schema 改为进程启动时初始化一次，不再随每个问答请求重复检查。
- 当前炉况快照与 8 小时趋势使用同一个 PostgreSQL 连接；当前值每个请求都重新读取。
- 8 小时趋势只按“最新诊断时间 + 最新记录版本 + 窗口 + 条数”精确复用；诊断版本变化立即失效。
- 最新传感器值查询改为 `sensor_registry` 对每个点位执行索引化 `LATERAL ... ORDER BY ts DESC LIMIT 1`。旧 SQL 会扫描并落盘排序约 381 万行，实测约 `3.62-4.74s`；新 SQL 返回同一组最新值，实测约 `0.25-14.5ms`。
- 只有 MCP 预取已包含所需变量、数值和时间时才跳过重复工具轮。图表、报表、多变量、比较、强制工具或预取不完整请求仍走完整工具流程。
- SSE 的准备事件不再重复查询和传输完整会话列表；最终事件仍返回完整列表，前端行为不变。

首次部署连接池时曾发现兼容层对所有 `INSERT` 都执行 `SELECT lastval()`，在文本主键会话表的新连接上导致事务中止。现已限定为只对自增主键表读取 `lastval()`，远端同连接可见性、提交后可见性和消息外键写入探针均通过。

## 十一、2026-07-15 近期炉况首 token 专项优化

### 1. 根因复核

初次 7 条近期炉况口语测试首 token 中位数为 `16.90s`，最快 `11.57s`、最慢 `48.57s`。数据库快照和 8 小时统计准备已是毫秒级，但链路还存在两次不必要的模型工作：

- 问题规范化移除“当前”“现在”后，部分炉况问题被误送到 RAG，增加 embedding、检索和知识证据预填充。
- 规范化口语关键词曾把“给我说一下”缩成单字“说”，使普通炉况和安全问题误进入非流式 MCP 工具选择。27B 未调用工具却先生成完整答案，导致 SSE 首 token 被整轮阻塞。

### 2. 实施内容

- 新增当前/近期炉况意图判断；该类问题使用每轮实时读取的最新炉况与完整 8 小时统计，跳过无关 RAG 和空工具选择。
- 明确知识意图仍保留 RAG，包括“为什么、原理、规则、阈值、制度、基线、知识库、文档、手册、引用、来源”。
- MCP 规范化关键词只允许长度至少为 2 的非空词参与命中；具体变量查询、统计、图表、报表和预取不完整场景仍使用 MCP。
- SSE 最终事件新增 `model_timing`，记录 Ollama 的 `prompt_eval_count`、`prompt_eval_duration_ms`、`eval_count`、`eval_duration_ms`、`load_duration_ms` 及折算吞吐率。

本次没有降低 RAG `top_k=6`、裁剪 8 小时炉况、减少固定规则或缩短回答上限，也没有缓存当前值或最终答案。
