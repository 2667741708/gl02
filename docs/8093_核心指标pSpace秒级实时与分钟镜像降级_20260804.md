## 2026-08-06 8768/8770 WebSocket 握手阻塞修复

- 现象：8768 与 8770 都处于监听状态并存在 TCP `ESTABLISHED`，但浏览器长期显示“连接中”；220.12 本机回环 WebSocket 验证同样无法及时完成握手/首帧。
- 根因：两个 asyncio WebSocket 服务都在事件循环中直接执行同步 I/O。8768 的 PostgreSQL 初始化/周期查询和 8770 的 pSpace `RealReadList` 一旦变慢，会阻塞整个事件循环，使新连接无法处理 HTTP Upgrade。
- 修复：8768 的 `build_init_payload()`、`build_tick_payload()` 与 8770 的 `build_init_payload()`、`read_frame()` 统一通过 `asyncio.to_thread()` 执行。8770 仍保持一个 `broadcast_loop`、每周期一次 `read_frame()`，未新增 pSpace 读取程序、任务、端口或读取频率。
- 部署：只重启既有 Windows 服务 `BFV4PreviewWs8768` 和计划任务 `V4BillboardPspace8770`。回滚备份为 `backups\ws_handshake_8768_8770_20260806_100745`；部署后 PID 为 8768=`3296`、8770=`2096`。
- 验收：服务器回环握手耗时分别为 8768=`0.031s`、8770=`0.016s`；8768 首帧为 PostgreSQL `init`，包含 118 个值；8770 实时 `tick` 包含 140 个流值，Billboard 映射 `133/133`、数值 `133/133`、缺失 `0`，验证通过。
- 回归测试：`python -m pytest tests/test_ws_event_loop_nonblocking.py`，用于防止同步数据读取重新进入 WebSocket 事件循环。
