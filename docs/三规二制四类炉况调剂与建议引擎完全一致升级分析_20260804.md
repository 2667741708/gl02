## 3. 先理解“四种调剂”到底是什么

四种调剂不是四种炉况，也不是四个互斥按钮。它们是同一炉况建议中的四个动作维度：

| 调剂方法 | 调的对象 | 主要影响 | 升级前系统状态 |
|---|---|---|---|
| 上部调剂 | 布矿、布焦、圈数、角位、下料闸开度、特殊布料 | 中心/边缘煤气流和料面 | 只有少量自然语言动作，未结构化到具体手段 |
| 下部调剂 | 风量、风温、喷煤、富氧 | 冶炼强度、热制度、透气性和风口状态 | 部分覆盖，但顺序、条件、幅度不完整 |
| 负荷调剂 | 焦炭负荷、净焦 | 中长期热平衡和料柱透气性 | 只有“调整负荷/适量净焦”等模糊文字 |
| 碱度调剂 | 炉料配比、理论/实际炉渣碱度 | 造渣、脱硫、炉缸状态 | 当前为零覆盖 |

例如“热制度下行”不是只对应下部调剂。原文要求它按顺序跨越下部调剂与负荷调剂；“管道”也可能同时用减风、减氧、特殊布料、减轻负荷和附加净焦。引擎必须输出一个有顺序、有门禁的动作链，而不是从八个标签中只选一张卡片。

- 八类静态模板见[action_templates.py:L3-L133](../调控结论生成引擎/recommendation/action_templates.py#L3-L133)，总计 34 条模板动作；
- 严重度只看主诊断分数，见[severity_mapper.py:L4-L15](../调控结论生成引擎/recommendation/severity_mapper.py#L4-L15)；
- 旧组合规则只有“热制度下行+低料线”和“热制度下行+边缘发展”两种。**这只是因为旧代码手写了两个 `if`，不是因为《三规二制》只有两个组合**；原文的四类调剂本来就会与低料线、边缘/中心气流、管道、悬料、压力制度和设备事件交叉组合；

这套旧实现的优点是只读、简单、能返回 loading/failed/ready 状态；缺点是无法表达“条件集合、动作顺序、现场配置值、数据缺失、原文证据和四类调剂协同”。v5 已用通用合并与冲突解析替代两条组合特判，任意主、次炉况都会合并候选动作并保留阻断或缺数据步骤。

### 4.1 八类模板逐项现状

| `hot` | 先减煤、减风温，持续偏热再转负荷 | 减煤和减风温方向有依据 | 缺 5.1.8.5 的加风加氧资格步骤和加重负荷 1.0～1.5% 步骤，现有顺序不完整 |

## 5. 第一优先级：修正两条总动作链

### 5.1 热制度下行动作链

原文顺序为“加风温 → 加煤 → 控氧减风 → 降低焦炭负荷 → 加净焦”，见[5.1.8.4:L399](./冀钢炼铁三规二制.md#L399)。当前 `cold` 模板先减风、减氧，又禁止立即恢复喷煤，之后才提高风温、加净焦，见[action_templates.py:L20-L36](../调控结论生成引擎/recommendation/action_templates.py#L20-L36)。这不是文字差异，而是动作顺序和喷煤方向冲突。

升级后的每一步应为：

1. **提高风温**：只有在热制度下行或低于规定水平、重负荷冷料影响将起作用、铁水温度低于 1460℃、理论燃烧温度偏低之一成立时才成为候选；常规每次 10～20℃、每小时不超过 50℃。严重下行且风口涌渣时才允许建议“经现场确认迅速提至批准的最高水平”。依据见[5.3.4.1:L523-L535](./冀钢炼铁三规二制.md#L523-L535)。
2. **增加喷煤**：热制度开始下行本身是原文允许条件之一；还可由料速加快、恢复炉况、重负荷冷因素触发，见[5.3.5.4:L611-L621](./冀钢炼铁三规二制.md#L611-L621)。但若已严重失常、减风降压、常压/低压/休风，减少或停止喷煤规则优先，本步骤必须标为 `blocked`，不能继续输出“加煤”。
3. **控氧减风**：炉况不顺或温度过高/过低时可减氧或临时停氧；减风必须带出具体触发证据，例如热制度严重下行、压差超限、低料线、管道/悬料等，不能仅因 `cold` 分数达到 60 就自动建议。
4. **降低焦炭负荷**：只有在前述下部调剂无余地、热制度仍低于规定水平或存在原文减轻负荷条件时进入；“降低焦炭负荷”应明确显示为“减轻负荷”，防止现场把“降低负荷”误解为减少焦炭绝对量。
5. **附加净焦**：作为最后一级补热手段。普通热制度下行、低料线、管道/悬料、短时停煤分别使用不同条件和定量依据；不再统一写“必要时适量加净焦”。

### 5.2 热制度上行动作链

原文顺序为“加风加氧 → 提高焦炭负荷 → 减煤 → 减风温”，见[5.1.8.5:L401](./冀钢炼铁三规二制.md#L401)。当前 `hot` 模板直接从减煤、减风温开始，只模糊地说持续偏热后再转负荷调剂，见[action_templates.py:L38-L52](../调控结论生成引擎/recommendation/action_templates.py#L38-L52)。

升级后的每一步应为：

1. **加风**：不是看到热制度上行就加风。必须先证明风量/风压平稳、风量低于批准的最佳风量、炉温充沛、渣铁出净、压差低于规定水平且现场可以承受；任何压差高、低料线、管道/崩悬、风口异常都会阻断。
2. **加氧**：只能在正常、稳定并与喷煤协同时逐步增加；富氧会提高理论燃烧温度并发展边缘煤气流，因此边缘已经发展、炉况不顺或温度过高时应阻断加氧并转为减氧/临停氧。
3. **提高焦炭负荷**：当热制度超过规定水平时，进入加重负荷候选；每次只允许 1.0～1.5%，并记录变更前后焦炭负荷值。当前“转入负荷调剂”必须改成可审计的动作。
4. **减煤**：在热制度上行时允许；同时需要说明喷煤具有约半个冶炼周期的热滞后，不能把执行后几分钟内的未变化误判为动作无效。
5. **减风温**：应及时、果断，一次减到经现场批准的需要水平，但禁止长期低风温；当风温用不上时要转入其他调剂并尽快恢复规定风温。依据见[5.3.4.2:L537-L553](./冀钢炼铁三规二制.md#L537-L553)。

若第一、第二步因安全边界不满足而被阻断，引擎应显示“本步骤不具备条件，已跳过”，再给后续可执行候选；不能为了字面遵守顺序而强行建议加风加氧。

## 7. 下部调剂：逐条升级清单

### 7.1 风量

原文见[5.3.3:L483-L519](./冀钢炼铁三规二制.md#L483-L519)。

**加风资格不是五条互相独立的推荐，而是一组承受条件：**

1. `LOW-BLAST-UP-01`：风量、风压平稳，且当前风量低于现场配置的最佳风量；
2. `LOW-BLAST-UP-02`：冶炼强度未达到目标，加风确有增产目标；
3. `LOW-BLAST-UP-03`：炉温充沛、渣铁出净，能承受增加风量；
4. `LOW-BLAST-UP-04`：压差低于现场规定水平；
5. `LOW-BLAST-UP-05`：若因提高顶压获得加风空间，必须记录顶压变更和高压运行门禁。

引擎只有在关键条件齐全时才给“具备加风候选条件”；缺“最佳风量、目标强度、渣铁出净”任一关键输入时显示 `needs_data`，不能把 `Q_blast` 偏低直接等同于应该加风。

**下列任一情况可形成减风候选，但每条证据必须单独保存：**

1. `LOW-BLAST-DOWN-01` 下料过快；
2. `LOW-BLAST-DOWN-02` 热制度严重下行；
3. `LOW-BLAST-DOWN-03` 顶压降低；
4. `LOW-BLAST-DOWN-04` 管道、崩料、偏料或悬料；
5. `LOW-BLAST-DOWN-05` 低料线；
6. `LOW-BLAST-DOWN-06` 休风料、低料线等难行料即将下达；
7. `LOW-BLAST-DOWN-07` 压差高于规定水平；
8. `LOW-BLAST-DOWN-08` 炉顶齿轮箱温度高于 70℃；
9. `LOW-BLAST-DOWN-09` 炉顶阀门箱温度高于 90℃；
10. `LOW-BLAST-DOWN-10` 铁口过浅、跑大流；
11. `LOW-BLAST-DOWN-11` 发生直接影响高炉生产的事故。

当前引擎覆盖了严重热制度下行、低料线、管道和悬料的一部分，其他事件既未接入，也没有把“为什么减风”作为结构化证据返回。

### 7.2 风温

原文见[5.3.4:L521-L553](./冀钢炼铁三规二制.md#L521-L553)。

**提高风温候选：**

1. `LOW-TBLAST-UP-01` 热制度向下；
2. `LOW-TBLAST-UP-02` 热制度低于规定水平；
3. `LOW-TBLAST-UP-03` 重负荷料引起的冷因素将起作用；
4. `LOW-TBLAST-UP-04` 铁水温度低于 1460℃；
5. `LOW-TBLAST-UP-05` 风口前理论燃烧温度低于正常水平；
6. `LOW-TBLAST-UP-06` 常规幅度每次 10～20℃、每小时累计不超过 50℃；严重下行且风口涌渣是唯一的快速提至最高批准水平例外。

**降低风温候选：**

1. `LOW-TBLAST-DOWN-01` 热制度向上；
2. `LOW-TBLAST-DOWN-02` 热制度高于规定水平；
3. `LOW-TBLAST-DOWN-03` 轻负荷料等热因素将起作用；
4. `LOW-TBLAST-DOWN-04` 炉温充足但炉况不顺；
5. `LOW-TBLAST-DOWN-05` 低压或休风恢复阶段的临时减风温；
6. `LOW-TBLAST-DOWN-06` 高炉憋压时临时减风温；
7. `LOW-TBLAST-DOWN-07` 理论燃烧温度过高；
8. `LOW-TBLAST-DOWN-08` 一次降至现场批准的需要水平，但禁止长期低风温；用不上风温时应转其他调剂并尽快恢复规定水平。

当前 `cold/hot` 只有“可提高/视情况降低”，没有上述条件、幅度、小时累计、例外和恢复要求。

### 7.3 喷煤

原文见[5.3.5:L555-L635](./冀钢炼铁三规二制.md#L555-L635)。建议引擎需要分成四组规则：

**质量资格：**

1. `LOW-PCI-QUALITY-01` 原煤灰分≤13.0%；
2. `LOW-PCI-QUALITY-02` 无烟煤 200 目细度达到 75%；
3. `LOW-PCI-QUALITY-03` 水分＜1.0%；
4. `LOW-PCI-QUALITY-04` 每周化学成分分析且成分相对稳定；
5. `LOW-PCI-QUALITY-05` 随煤量增加需高风温、高富氧并保持燃烧、喷吹均匀稳定。

这些是“是否具备加煤资格”的门禁，不应混成一条普通观察文字。

**机理与滞后：**煤量增加会提高煤气量和氢还原能力，但煤粉燃烧分解吸热、使理论燃烧温度降低；焦炭负荷增加、高温区下移；热影响约滞后半个冶炼周期。每次喷煤建议必须返回预计观察窗口，不能固定用当前模板的 5～15 分钟复查判定最终热效果。

**允许增加喷煤的五种情况：**

1. `LOW-PCI-UP-01` 顺行良好、风量大且有计划增煤；
2. `LOW-PCI-UP-02` 热制度向下；
3. `LOW-PCI-UP-03` 料速加快；
4. `LOW-PCI-UP-04` 炉况恢复过程中；
5. `LOW-PCI-UP-05` 重负荷等冷因素将起作用。

**允许减少或停止喷煤的六种情况：**

1. `LOW-PCI-DOWN-01` 计划减煤；
2. `LOW-PCI-DOWN-02` 热制度向上；
3. `LOW-PCI-DOWN-03` 减风降压；
4. `LOW-PCI-DOWN-04` 常压、低压、休风时停止喷吹；
5. `LOW-PCI-DOWN-05` 炉况严重失常时停止喷吹；
6. `LOW-PCI-DOWN-06` 计划长期休风前提前停喷。

当增煤和停煤规则同时命中时，安全/失常/低压规则优先；输出应明确“原本热制度下行允许加煤，但因严重失常被阻断”。这正是当前 `cold` 模板无法表达的条件冲突。

**操作安全与联络：**

1. `LOW-PCI-OPS-01 / 5.3.5.2.6.1`：先送风后送煤；停喷时先停煤后停风；
2. `LOW-PCI-OPS-02 / 5.3.5.2.6.2`：停煤吹扫后尽快停吹扫风，不允许长时间空吹；紧急拉风立即通知喷吹站停煤并处理管内煤粉；
3. `LOW-PCI-OPS-03 / 5.3.5.2.6.3`：喷吹罐工作压力高于热风压力 50 kPa 以上，防止倒灌；
4. `LOW-PCI-OPS-04 / 5.3.5.2.6.4`：正常生产保持连续、稳定、均匀喷吹和准确计量；
5. `LOW-PCI-SAFE-01 / 5.3.5.3.1`：巡视喷吹和风口视孔，异常立即处理并报告值班工长；
6. `LOW-PCI-SAFE-02 / 5.3.5.3.2`：喷吹不畅、煤枪或煤支管堵塞时及时排通；
7. `LOW-PCI-SAFE-03 / 5.3.5.3.3`：煤枪前端烧损或枪阀破损及时更换，并保持合适伸出长度；
8. `LOW-PCI-SAFE-04 / 5.3.5.3.4`：喷吹阀门保持灵活，煤阀失灵时及时更换；
9. `LOW-PCI-SAFE-05 / 5.3.5.3.5`：喷吹作业防止煤气中毒；
10. `LOW-PCI-SAFE-06 / 5.3.5.3.6`：插拔煤枪时禁止站在煤枪正面；
11. `LOW-PCI-SAFE-07 / 5.3.5.3.7`：排煤粉时避免明火；
12. `LOW-PCI-SAFE-08 / 5.3.5.3.8`：风管灌煤时禁止打开视孔小盖排煤，立即停喷并待休风处理；
13. `LOW-PCI-SAFE-09 / 5.3.5.3.9`：喷枪烧坏、风口严重破损、风管严重结焦、风口涌渣或连续升降时，对应风口暂停喷吹；
14. `LOW-PCI-SAFE-10 / 5.3.5.3.10`：分配器定期开盖清扫，作为维护到期检查而非实时调参动作。

建议页应显示这些前置、禁止、联络和维护项，而不是把它们塞进模型自由文本。`SAFE-05` 至 `SAFE-10` 多数依赖人工或设备事件；未接入时应显示数据来源不足，不应默认“安全条件已满足”。

### 7.4 富氧

原文见[5.3.6:L637-L663](./冀钢炼铁三规二制.md#L637-L663)。

1. `LOW-O2-EFFECT-01` 富氧率每提高 1%，原文给出产量约提高 3%的机理说明；该数值只能作为原文效果提示，不能自动换算成推荐幅度；
2. `LOW-O2-EFFECT-02` 富氧率每提高 1%，理论燃烧温度约提高 35℃，必须进入温度上限预测；
3. `LOW-O2-EFFECT-03` 富氧会发展边缘煤气流，边缘已发展时加氧应被阻断；
4. `LOW-O2-DOWN-01` 炉况不顺、温度过高或过低时，减氧或临时停氧有利于恢复；
5. `LOW-O2-STABLE-01` 正常生产保持富氧率稳定，给氧和停氧逐步增减，并与喷煤协同；
6. `LOW-O2-SAFE-01` 至 `06`：氧阀室禁火、氧管禁用钢铁件敲击、动火前停氧吹扫、专用阀门禁油、送停氧预先通知鼓风机和调度室、富氧鼓风发生烧穿时先停氧后减风。

当前 `cold/channel` 的“小幅减氧”和 `hot` 的“禁止继续增氧”只覆盖方向，没有稳定、渐变、协同、边缘效应、通知和事故顺序。

## 8. 负荷调剂：逐条升级清单

原文见[5.3.7-5.3.8:L665-L719](./冀钢炼铁三规二制.md#L665-L719)。

### 8.1 加重负荷

以下任一项可进入候选，但必须经热状态、透气性和现场负荷定义复核：

1. `LOAD-UP-01` 热制度超过规定水平；
2. `LOAD-UP-02` 热量充足，风温/喷煤/加湿等参数尚未达到规定使用水平；
3. `LOAD-UP-03` 上部调剂后煤气利用率将提高；
4. `LOAD-UP-04` 喷吹量增加或喷吹物质量改善；
5. `LOAD-UP-05` 焦炭质量改善；
6. `LOAD-UP-06` 入炉铁份降低。

输出动作必须使用“加重焦炭负荷（矿/焦比上调）”并展示每次 1.0～1.5%的原文边界，不能只写“调整负荷”。

### 8.2 减轻负荷

1. `LOAD-DOWN-01` 管道、崩料、悬料；
2. `LOAD-DOWN-02` 长时间慢风；
3. `LOAD-DOWN-03` 焦炭质量变差；
4. `LOAD-DOWN-04` 入炉铁份提高；
5. `LOAD-DOWN-05` 渣皮脱落；
6. `LOAD-DOWN-06` 冷却设备漏水；
7. `LOAD-DOWN-07` 热制度低于规定水平且其他参数已无调剂余地；
8. `LOAD-DOWN-08` 上部调剂后煤气利用率将降低；
9. `LOAD-DOWN-09` 计划长时间休风；
10. `LOAD-DOWN-10` 布料器长时间不能正常工作；
11. `LOAD-DOWN-11` 负荷调剂坚持勤调剂、量相当；加重每次 1.0～1.5%，减轻应力求一次达到现场决定的目标。

“一次到位”不等于系统自己计算绝对目标。建议引擎必须要求现场给定/批准目标焦炭负荷，并只校验计划是否满足原文节奏。

### 8.3 附加净焦

1. `NET-COKE-01` 热制度下行或渣铁温度过低；
2. `NET-COKE-02` 因故大量减煤或短时停煤；
3. `NET-COKE-03` 管道、悬料；
4. `NET-COKE-04` 悬料恢复后，按料崩后的料线深度确定量；
5. `NET-COKE-05` 低料线，按持续时间和实际深度确定量；
6. `NET-COKE-06` 长时间休风，加入量由高炉作业长决定；
7. `NET-COKE-07` 热洗炉，由高炉作业区提出并经事业部同意后集中加入。

当前 `cold/lowline` 的“必要时/根据亏料深度适量加净焦”只覆盖 `01/05` 的一部分，也未保留职责审批层级。

## 9. 碱度调剂：逐条升级清单

原文见[5.3.9:L721-L735](./冀钢炼铁三规二制.md#L721-L735)，目标二元碱度 `CaO/SiO2=1.15～1.22`、炉渣 `MgO=8～12%` 见[5.1.7:L383-L389](./冀钢炼铁三规二制.md#L383-L389)。

1. `BASICITY-01` 烧结矿碱度或炉料配比变化时，触发重新核算；
2. `BASICITY-02` 实际炉渣碱度超出控制范围时，触发调剂候选；
3. `BASICITY-03` 铁水 `[S]` 过高或过低时，触发脱硫/造渣复核；
4. `BASICITY-04` 准备长时间休风时，进入专项方案；
5. `BASICITY-05` 停炉或开炉时，进入专项方案；
6. `BASICITY-06` 炉缸堆积时，进入专项方案；
7. `BASICITY-07` 任何碱度方向/调剂量输出前，必须先核算当前配比的理论碱度，与实际炉渣碱度对比，再决定方向和量。

最重要的安全边界是：5.3.9 只规定“何时调”和“先计算再决定”，没有给一条通用的加石灰/减石灰固定幅度。因此新引擎在缺少理论配料计算、实际 `r2`、炉次时间对齐或批准目标时，只能输出 `needs_data`，不得猜方向和剂量。

本项目已经具备可接入的数据入口，但尚未进入当前 recommendation 快照：

- 命名炉渣视图包含 `r2/r3/r4` 等字段，见[mes数据集:L131-L140](./mes数据集.md#L131-L140)；
- 烧结矿化验有 `R2`，见[mes数据集:L456-L487](./mes数据集.md#L456-L487)；
- 铁水硫 `S` 有确认映射，见[imes_relay_mcp_server.py:L112](../高炉前端数据/智能助手/mcp/imes_relay_mcp_server.py#L112)；
- 当前只读查询入口为[炉渣查询:L963-L982](../高炉前端数据/智能助手/mcp/imes_relay_mcp_server.py#L963-L982)和[烧结矿查询:L985-L1013](../高炉前端数据/智能助手/mcp/imes_relay_mcp_server.py#L985-L1013)。

这些化验数据存在炉次和发布时间滞后，不能与一分钟传感器值当成同一时刻。建议中必须显示样本炉次、取样/发布时间、数据新鲜度和关联置信度。

## 10. 每一条新建议应返回什么

建议动作的最小结构应升级为：

```json
{
  "id": "LOW-TBLAST-UP-06",
  "scheme": "lower",
  "source_refs": ["5.1.8.4", "5.3.4.1.6"],
  "name": "分步提高风温",
  "user_facing_text": "经现场确认后，每次提高10～20℃，每小时累计不超过50℃",
  "sequence_rank": 10,
  "status": "eligible",
  "trigger_logic": "any",
  "evidence": [],
  "required_inputs": [],
  "missing_inputs": [],
  "preconditions": [],
  "blocking_conditions": [],
  "delta": {"min": 10, "max": 20, "unit": "℃"},
  "hourly_limit": {"max": 50, "unit": "℃/h"},
  "observe_items": [],
  "effect_window_minutes": null,
  "operator_confirm_required": true,
  "read_only": true
}
```

`status` 固定使用：

- `eligible`：证据和条件完整，可交现场确认；
- `blocked`：方向虽匹配，但被安全/工况条件阻断；
- `needs_data`：缺少关键输入，不能判定；
- `manual_confirm`：原文属于特殊布料、坐料、休风、热洗等人工流程；
- `not_applicable`：当前事实不满足。

前端不得只展示前三条而隐藏阻断原因。首页可以保留前三条摘要，但参数优化页必须能展开完整动作、原文依据、缺失输入、禁止项和复查窗口，并遵守“文字可恢复展示”要求。

## 11. 数据接入矩阵

| 决策输入 | 当前真实情况 | 升级要求 |
|---|---|---|
| 风量/风压/顶压/压差/风温/喷煤/富氧/TFT/料线 | 传感器链路中多数已有 | 适配器必须把所需当前值、趋势、基线和质量标志全部传给策略层，不再只主动映射 P_top/T_top/L |
| 铁水温度 | 现有 `T_taphole_1/2` 是出铁口温度，不等于铁水化验温度 | 新建经验证的 `hot_metal_temperature` 特征；来源未确认前 `LOW-TBLAST-UP-04=needs_data` |
| 渣铁出净、风口涌渣、跑大流、事故状态 | 当前多为人工/外部事件 | 设计现场只读确认字段和来源时间，不从模型文本猜测 |

| 焦炭质量、入炉铁份、负荷值、料批结构 | 当前引擎未接入 | 建立炉批/质检到当前炉况的时间对齐和质量状态 |

| 齿轮箱/阀门箱温度、冷却漏水、布料器故障 | 当前建议门禁未覆盖 | 接设备状态或人工事件；阈值按原文 70℃/90℃保留 |

6. **已分离展示严重度与动作资格**：[severity_mapper.py](../调控结论生成引擎/recommendation/severity_mapper.py)仍为页面严重度/复查周期提供分数映射；动作资格改由具体阈值、数据质量和事件硬条件决定。

### 12.2 语言层

原文证据必须保留原句，但生产前端继续执行项目固定显示规范：内部 `cold/hot` 显示为“热制度下行/热制度上行”，不向现场直接显示旧炉况称呼。实现方式应为：

- `source_quote` 保留原文；
- `user_facing_text` 使用现场批准的新名称；
- 不改数据库 `cold/hot` 键、阈值和历史记录。

这叫“规则语义一致、展示术语受控”，不能为了表面逐字相同破坏现有生产命名规范。

## 13. 完全一致的验收测试

### 13.1 源文件覆盖

1. DOCX→Markdown 有序文本片段相等；
2. 5.1.8.1-5 与 5.3.1-5.3.9 每个动作/条件条款均有唯一策略 ID；
3. 所有策略 ID 都能反查原文、代码和测试；
4. 新旧版本差异报告明确哪些条款为自动证据、人工证据或暂缺数据。

### 13.2 关键场景合同

1. 轻度热制度下行且顺行：首选加风温，其后允许加煤；不得输出当前“禁止立即恢复喷煤”的无条件结论；
2. 热制度下行但严重失常：加煤候选显示 `blocked`，停止喷煤规则优先；
3. 热制度上行且加风条件齐全：顺序为加风/加氧→加重负荷→减煤→减风温；
4. 热制度上行但压差高或边缘发展：加风/加氧明确阻断，再显示后续可行候选；
5. 低料线：减风、净焦量依据料线深度/持续时间，缺任一信息不输出具体量；
6. 管道：特殊布料、净焦后补矿、坐料分别带前置条件，不能合成一句“处理管道”；
7. 高压运行：坐料候选必须被阻断；
8. 碱度超限但理论配料未算：只输出重新核算，不给调整方向/剂量；
9. 炉渣 R2、烧结矿 R2、铁水 S 的炉次/发布时间不一致：标记数据时序风险；
10. 所有建议均为 `read_only=true`，不存在生产控制 API。

### 13.3 前端验收

按项目浏览器与视口矩阵验证首页和参数优化页；重点检查四类分组、动作顺序、阻断理由、原文依据、长文本可展开、loading/empty/error/needs_data 状态和无横向溢出。首页前三条摘要必须与参数优化页同一动作序列逐字一致，但参数优化页要能恢复查看全部内容。

## 14. 推荐实施顺序

1. **第一阶段：规则目录与只读审计（本地核心完成）**。策略目录和完整只读返回已落地；历史回放的 shadow 差异报告仍待运行。
2. **第二阶段：修正热制度上下行动作链（完成）**。已解决顺序和喷煤冲突，加入条件/阻断状态。
3. **第三阶段：补全上部、风量、风温、喷煤、富氧和负荷输入（接口完成、真实数据接入未完成）**。没有数据的动作保持 `needs_data`。
4. **第四阶段：接入炉次化验和碱度计算**。先完成理论/实际碱度核算，再允许生成方向性建议。
5. **第五阶段：现场规则评审与回放**。用历史炉次和人工复核对比，不以模型语言流畅度代替工艺签字。
6. **第六阶段：升级 8767/前端合同（本地适配完成、远端未部署）**。保持只读，经影子回放、完整详情前端、浏览器矩阵和现场主用 Edge 冒烟后再替换远端历史版本。

## 15. 一句话理解

升级前的 v4 是“看到八种炉况标签，就拿出一组固定建议”；v5 核心已经改为“先确认炉况事实和数据质量，再从四种调剂规则中筛选候选，按三规二制规定的先后顺序排队，经过安全门禁和现场权限过滤，最后把可做、不能做、缺数据和为什么全部说清楚”。
