# 220.12 Ollama 27B / 30B 自动拉起链路核查与单模型修复

## 结论

220.12 并不是让 27B 和 30B 各自启动一套 Ollama 监听服务。当前只有一套
Windows 自动服务 `BFOllama11434`，它启动一个 `ollama serve`，统一监听
`0.0.0.0/[::]:11434`；具体模型由 Ollama 在收到 API 请求时加载为内部 runner，
runner 使用随机回环端口，不单独对外监听。

- **27B 当前有明确的自动拉起/常驻链路**：每分钟运行的
  `\BlastFurnaceServices\BFOllama11434HealthCheck` 会向
  `chiqiong-blast-furnace:latest` 发送一次极短 `/api/chat`，并带
  `keep_alive=24h`。这既是模型健康检查，也是 27B 的预热与续驻程序。
- **30.5B 当前没有启用中的自动拉起程序**。服务器保存了
  `bf-diagnosis-runtime:v1` 与 `chiqiong-blast-furnace:latest_M`
  两个 30.5B 标签，但二者 digest 相同；当前启用的 Ollama 健康检查、
  8092、8093 和 8094 配置都实际指向 27B。`/api/ps` 也只显示 27B。
- 核查阶段的 `OLLAMA_MAX_LOADED_MODELS=2` 只表示最多允许同时驻留两个模型，
  不会自动加载两个大模型。2026-07-26 14:37 已按生产要求改为 `1`，并在代理
  和模型清单两层阻止 30.5B 再被旧请求加载。

## 27B 的自动预热与故障自恢复

实际自动程序是计划任务：

```text
\BlastFurnaceServices\BFOllama11434HealthCheck
```

它自 2026-07-07 10:24:22 起启用，重复间隔为 `PT1M`（每 1 分钟），执行：

```text
powershell.exe
  -File ...\tools\check_managed_nssm_service_health.ps1
  -ConfigPath ...\tools\service_configs\22012_BFOllama11434.json
```

配置中的关键 POST 为：

```json
{
  "url": "http://127.0.0.1:11434/api/chat",
  "model": "chiqiong-blast-furnace:latest",
  "stream": false,
  "keep_alive": "24h",
  "options": {
    "num_predict": 1,
    "temperature": 0,
    "think": false
  }
}
```

因此，27B 的完整自动链是：

```text
Windows 自动服务 BFOllama11434
  -> ollama serve 监听 11434
  -> 每分钟健康任务 POST /api/chat
  -> 加载/续驻 chiqiong-blast-furnace:latest（27.8B）
```

健康脚本在 TCP、HTTP 或模型 POST 失败时会执行
`Restart-Service BFOllama11434 -Force`。健康日志已记录 2026-07-26
12:34:12 因 `/api/chat` 超时触发重启，12:34:45 恢复为 `Running`；这证明
该程序不仅预热 27B，也会自动恢复 Ollama 监听服务。

8092、8093、8094 也都把真实 `BF_LLM_MODEL` 指向
`chiqiong-blast-furnace:latest`，业务问答同样会触发或刷新 27B，但它们是
Ollama 客户端/代理，不是 `11434` 监听器的启动程序。

## 30.5B 当前状态

`/api/tags` 的模型身份如下：

| 标签 | 参数量 | 量化 | digest 关系 |
|---|---:|---|---|
| `chiqiong-blast-furnace:latest` | 27.8B | Q4_K_M | 与 `latest_s` 相同 |
| `chiqiong-blast-furnace:latest_s` | 27.8B | Q4_K_M | 与 `latest` 相同 |
| `bf-diagnosis-runtime:v1` | 30.5B | Q4_K_M | 与 `latest_M` 相同 |
| `chiqiong-blast-furnace:latest_M` | 30.5B | Q4_K_M | 与 `bf-diagnosis-runtime:v1` 相同 |

核查时 `/api/ps` 只有：

```text
chiqiong-blast-furnace:latest
parameter_size=27.8B
context_length=32768
size_vram=18768731136
```

没有 30.5B runner。当前没有服务配置、健康任务或活跃代理命令行把
`bf-diagnosis-runtime:v1` / `latest_M` 作为真实模型自动请求。

代理后端现在把浏览器传入的 `model` 视为显示元数据，不再原样转发。未设置
`BF_LLM_MODEL` 时先读取 `/api/ps` 当前驻留模型；若没有驻留模型，再读取
`/api/tags` 选择一个已安装模型。这样不会绑定 30.5B，11434 服务端可以替换
当前模型。即使旧前端仍提交某个模型别名，实际问答也由 11434 的模型发现结果决定。

- `BFBaselineProxy8092` 的 JSON 显式设置 27B；
- `BFV4PreviewProxy8093` 的参数和环境显式设置 27B；
- `V3AutoPreviewProxy8094` 的 runner 显式设置 27B；
- `BFOllama11434HealthCheck` 的 POST 显式设置 27B。

修复前，30.5B 是“已安装、可按请求加载”，不是“自动预热、自动常驻”。
修复后，它的两个 manifest 已移动到可恢复隔离目录，`/api/tags` 不再暴露
30.5B，直接向 11434 请求该标签返回 HTTP 404。
