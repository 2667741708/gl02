## 1. 结论

附件提出的“规则控制 + 模型选择 + 执行反馈”“渐进式工具披露”“业务语义工具”
总体合理，也符合MCP Host负责管理多个Client/Server、汇总工具并路由调用的官方
架构。但8093当前实现的“按需”只覆盖**按问答启动一个固定stdio脚本**，没有覆盖：

- 多MCP服务注册与连接管理；
- 由业务领域选择一个或多个服务；
- 跨服务统一工具注册表；
- 目录中`executor.service/tool`到真实Client的执行路由；
- MES证据在后续对话中的结构化继承。

因此，8093可以稳定调用GL02传感器工具，却不能可靠执行MES/IMES炉次和化验工具。

## 2. 当前实现与缺口

### 2.1 单服务固定启动

[问答代理](../高炉前端数据/智能助手/backend/ollama_proxy_server.py#L136-L146)
只有一个`MCP_DATA_SERVER_PATH`。每次进入工具循环后，仅为该脚本创建一个
`StdioServerParameters`，再调用一次`list_tools()`：

- [创建单个stdio服务](../高炉前端数据/智能助手/backend/ollama_proxy_server.py#L4497-L4537)
- [模型工具循环与两轮上限](../高炉前端数据/智能助手/backend/ollama_proxy_server.py#L4644-L4751)

默认脚本是`bf_data_mcp_server.py`，所以8093看到18个GL02/报表/目录工具；独立的
[IMES只读MCP](../高炉前端数据/智能助手/mcp/imes_relay_mcp_server.py#L571-L1013)
提供13个工具，但没有加入同一次问答的工具集合。

### 2.2 目录发现与执行没有闭环

[炉次与化验目录](../高炉前端数据/智能助手/mcp/catalog/heat_analysis.json#L5-L58)
把对象执行器声明为`imes-relay-mcp`，但当前Host没有按`executor.service`选择Client。
目录能告诉模型“应该调用`query_hot_metal_chemistry_by_heat`”，实际工具白名单中却
没有该工具。

目录中的高炉炉次还引用`query_imes_business`，当前IMES MCP没有这个工具；真实入口
是`query_imes_object`、`query_imes_variables`等。目录合同和运行工具已经漂移。

### 2.3 现有“计划—执行状态机”仍是单服务循环

[九阶段总表](../PT/MCP智能工具系统九阶段升级总表.md)把阶段4标为第一版完成，
但当前代码没有独立计划对象、依赖DAG、server_id或跨Client执行器。实际结构仍是：

```text
单个MCP list_tools
→ 27B生成下一次tool_call
→ 当前session.call_tool
→ 最多再规划一次
```

这足以处理同一GL02 MCP中的目录、统计和绘图，不足以处理“MES炉次→MES化验”以及
以后“MES炉次→GL02时间窗→计算/绘图”的跨服务任务。

### 2.4 对话状态缺少MES业务主键

[结构化对话状态](../高炉前端数据/智能助手/backend/mcp_conversation_context.py)
当前保存传感器对象、相对时间窗、分析目标、图表偏好及精简工具证据，但没有保存：

- `current_heat_no/previous_heat_no`；
- MES对象、账号profile和正式时间字段；
- 试样号、取样时间、发布时间；
- 可复用的`evidence_id`与数据有效期。

因此，即使某一轮独立查到MES数据，后续“跟上一炉比呢”“把这几炉画出来”也缺少
稳定的业务引用。

## 3. 对附件策略的判断

### 3.1 建议保留

- Host/Client/Server分层；
- 确定性规则先缩小领域和权限；
- 模型只在少量候选工具中选择；
- JSON Schema、参数范围和只读白名单双重校验；
- 工具返回结构化错误和可修正字段；
- 高频业务使用语义工具，不让模型拼SQL；
- L0-L4风险分级，生产控制写入保持禁止；
- 工具调用、来源、耗时、结果摘要和错误持久化。

### 3.2 当前阶段不建议直接采用

1. **不建议先上模型生成代码执行。** 当前只有2个服务、31个工具，代码沙箱的
   安全和运维成本高于收益。应先完成Host侧多Client、复合工具和DAG执行。
2. **不建议把`search_tools/describe_tool/call_tool`都暴露给模型作为必经步骤。**
   这会新增规划轮次。服务/工具初筛应先由Host完成；当工具超过约100个或服务显著
   增多时，再增加渐进式搜索。
3. **不建议简单把模型循环提高到6-10步。** 8093的27B延迟较高。高频任务应由
   一次复合工具完成；开放式任务使用显式DAG，模型最多一次初始计划和一次修正。
4. **不建议向生产模型开放`query_imes_readonly_sql`。** 即使服务端限制为只读，
   生产问答仍应只开放对象/字段白名单工具；任意只读SQL保留给运维诊断角色。

## 4. 推荐目标架构

```text
用户问题
  ↓
领域路由器（GL02 / MES / knowledge / calculation，可多选）
  ↓
MCP Client Manager
  ├─ gl02-data client
  └─ imes-readonly client
  ↓
按领域加载并缓存少量工具Schema
  ↓
计划器生成业务DAG
  ↓
策略校验 → 拓扑执行 → 证据存储
  ↓
确定性事实格式器 / 模型解释
```

建议将Host侧代码独立到：

```text
高炉前端数据/智能助手/backend/mcp/
  server_registry.py       # 服务清单、领域、启动方式和健康状态
  client_manager.py        # stdio连接、空闲TTL、重连和关闭
  domain_router.py         # 高置信度领域选择，可返回多个领域
  tool_registry.py         # 命名空间、Schema缓存和工具到Client映射
  plan_contract.py         # PlanStep、依赖、输入引用和预算
  executor.py              # 校验、拓扑执行、超时和一次修正
  evidence_store.py        # 精简证据与后续对话引用
  errors.py                # 稳定错误码
  audit.py                 # run/call/evidence审计
```

服务清单建议使用配置而不是单一脚本环境变量：

```json
{
  "servers": [
    {
      "server_id": "gl02-data",
      "domains": ["sensor", "chart", "report"],
      "transport": "stdio",
      "enabled": true,
      "idle_ttl_seconds": 300
    },
    {
      "server_id": "imes-readonly",
      "domains": ["heat", "hot_metal", "slag", "feed"],
      "transport": "stdio",
      "enabled": true,
      "idle_ttl_seconds": 300
    }
  ]
}
```

工具必须使用Host内唯一命名空间，例如：

```text
gl02.query_sensors
gl02.plot_trends
imes.query_heat_context
imes.query_hot_metal_chemistry_by_heat
imes.get_current_previous_heat_si_summary
```

## 5. MES/IMES优先补齐的业务工具

### 5.1 原子工具

- `imes.get_current_heat_context(as_of_time, furnace_id)`：返回当前正式`meltno`、
  开口/堵口状态、数据时间和判定依据；
- `imes.get_previous_heat(heat_no)`：按MES正式顺序返回上一炉次；
- `imes.get_heat_chemistry(heat_no, components)`：返回全部试样、取样时间、发布时间；
- `imes.aggregate_heat_component(heat_no, component, method)`：明确样本数、均值、
  最小/最大值和缺失值策略。

### 5.2 高频复合工具

```text
imes.get_current_previous_heat_si_summary(as_of_time, furnace_id)
```

一次调用内部完成：

```text
当前正式炉次
→ 上一正式炉次
→ 上一炉次全部有效铁水试样
→ Si数值与取样时间校验
→ count/mean/min/max/values
```

该工具应返回`current_heat_no`、`previous_heat_no`、`si_values`、`si_avg`、
`sample_count`、`sample_times`、`source_object`、`as_of_time`和`quality`。

## 6. 真正的“按需”策略

1. **始终只加载轻量服务索引**：server_id、领域、别名、风险级别、健康状态；
2. **Host先做领域路由**：明确“炉次/铁水/炉渣/进料/硅”直接选择IMES；明确
   “顶压/风量/炉温/趋势”选择GL02；组合问题同时选择两者；
3. **按需连接Client**：第一次命中时启动stdio服务，随后保持5分钟空闲TTL；
4. **按需加载Schema**：只把候选领域的3-8个工具交给模型；`tools/list`结果按
   server版本或哈希缓存；
5. **Host负责工具到Client的路由**：模型只返回命名空间工具名，不接触脚本路径；
6. **依赖任务一次规划**：执行器按DAG执行，不要求27B在每个数据库结果后重新推理；
7. **证据引用进入对话状态**：保存炉次号、试样引用和`evidence_id`，不保存密码、
   SQL或整表原文；
8. **只把摘要交给模型**：大结果在执行器内过滤、聚合，避免上下文膨胀。

## 7. 分阶段实施建议

### P0：修复当前MES不可调用

- 建立两服务registry和多Client manager；
- 修正`heat_analysis.json`中的不存在工具名；
- 将IMES工具加入8093按需候选集合；
- 增加MES确定性领域路由；
- 增加当前/上一炉次Si复合工具；
- 保持现有GL02固定快速路径不变。

### P1：对话与证据

- 扩展对话状态保存炉次、试样和证据ID；
- 建立`mcp_runs/mcp_call_events/mcp_evidence_links`；
- 后续追问优先复用证据，超出有效期再重查。

### P2：性能与渐进式发现

- stdio Client空闲TTL与异常重连；
- 工具Schema缓存和list-changed失效；
- 服务超过5个或工具超过约100个后，再引入`search_tools(detail_level)`；
- 暂不引入模型生成代码执行，除非出现大规模跨服务数据处理且具备专用沙箱。

## 8. 验收矩阵

必须同时检查答案、领域、服务、工具、参数和证据：

| 问题 | 期望服务 | 期望工具/流程 |
|---|---|---|
| 当前炉次是多少 | IMES | `get_current_heat_context` |
| 上一炉次Si平均值 | IMES | `get_current_previous_heat_si_summary` |
| 这炉与上一炉Si比较 | IMES | 复用炉次证据或两炉聚合 |
| 上一炉出铁期间顶压走势 | IMES + GL02 | 炉次时间窗→GL02趋势 |
| 把最近10炉Si和铁水温度画出来 | IMES | 炉次聚合→绘图 |
| 当前顶压是多少 | GL02 | 保持现有快速路径 |

验收指标：

- 服务选择准确率、工具选择准确率、业务主键正确率均为100%；
- 常用MES单服务问题不超过1次模型规划；
- 复合高频问题只调用1个复合工具；
- 跨服务问题只进行1次计划，执行器内部完成依赖步骤；
- `TOOL_NOT_ATTACHED`、`SERVER_UNAVAILABLE`、`NO_DATA`、
  `AMBIGUOUS_OBJECT`、`PLAN_BUDGET_EXCEEDED`分别返回；
- 所有回答带来源、数据时间、样本数和缺失说明；
- 8093升级不得重启8768/8770或修改MES/Vastbase数据。

## 9. 外部依据

- [MCP Architecture](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)：
  Host为每个Server建立独立Client，并可将多个Server的工具汇总到统一注册表；

  工具使用JSON Schema，多个Server由AI应用统一组合；
- [Anthropic: Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)：
  大量工具时可用渐进式披露和执行环境过滤中间数据，同时明确代码执行会增加沙箱、
  资源限制和监控成本。
