# 8093 跨数据库按需 MCP 口语验收（2026-08-05）

追踪编号：`AUDIT-8093-CROSS-DATABASE-MCP-20260805`

## 结论

8093 的多 MCP host 具备在同一次问答中调用 MES/Vastbase 与 GL02 数据服务的
基础能力，但当前复杂口语的端到端可靠性不达生产验收标准。服务注册和按需挂载正常，
主要缺陷位于“单一路径确定性快捷计划”与“模型多轮规划/最终回答组装”。

## 已证实的跨库调用

一次成功进入两库的工具轨迹为：

1. `imes-readonly -> imes__query_hot_metal_chemistry_by_heat`
2. `gl02-data -> query_gl02_sensors(T_body_L13_C, P_top)`

MES 返回 `2#20260805-072` 的 `Si=0.16%`、`Mn=0.26%`；GL02 返回
`T_body_L13_C=94.84`、时间 `2026-08-05T22:27:00`，并已取得 `P_top` 工具结果。
但最终回答输出被截断，所以只能判为“跨库工具层成功、回答层不完整”。

## 根因定位

8093 先建立四服务领域候选，再执行工具规划。当前代码把四类确定性计划写成：

```python
deterministic_plan = imes_plan or chart_plan or standard_plan or sensor_plan
```

因此一个问题同时命中 MES 与传感器时，只能选中第一个非空计划并直接格式化返回；
不会合并两个计划。未命中快捷计划时才进入模型规划器，模型可能调用多个服务，但会受到
工具轮数、调用次数、单工具超时、目录发现和重复调用影响。

其他观察：

- 模型会把正式炉次号 `2#20260805-072` 简化成 `072` 或 `20260805-072`。
- `gl02-data` 与 `gl02-extended` 存在部分能力重叠，模型可能把 `P_top` 错派到历史炉况工具。
- 规划器可能先调用 `find_gl02_variables`，消耗工具预算，却未进入真实值查询。
- 工具均成功不保证最终回答完整；回答仍受输出上限和最终合成影响。

## 推荐修复顺序

1. 把单一 `deterministic_plan` 改成可并行/顺序执行的 `deterministic_plans[]`，允许同一问答同时包含 MES、传感器和炉身温度子计划。
2. 新增一个后端复合工具 `query_cross_source_snapshot`，参数固定为炉次化验字段、传感器变量和时间策略；后端并发查询两库并返回统一 JSON，避免模型自己编排目录与多轮工具。
3. 对 `meltno` 做服务端规范化和严格保留 `2#YYYYMMDD-NNN`，不依赖模型传参准确性。
4. 按领域缩小工具集并消除能力重叠：普通传感器只能交给 `gl02-data`，炉身层位和历史诊断分别交给 `gl02-extended` 的明确工具。
5. 对同一轮独立只读工具并发执行；目录查询不计入业务工具轮数，重复工具参数直接命中缓存或拒绝。
6. 对跨库回答使用确定性结果格式化器，检查每个请求字段都有 `value/time/source/missing` 后再返回，禁止半截回答宣称成功。

本轮只做生产只读验收和本地审计工具增强，没有修改或重启 8093/8768/8094/8770。
