## 已证明的问题

“下面是风温数据，请分析波动”会被风温、最近、温度或趋势等关键词引到现场查询。
初始23项17fail/6pass；之前4个纯用户数据问题的只读探针均发现错误现场路由。
即使任务计划挡住纯数据请求，实际alias、分析bundle、duration和clock解析仍可能把用户提供的对象/时间混入另行要求的查询。

[user_data_scope](../../高炉前端数据/智能助手/backend/qa_task_plan.py:162)现在识别给定输入及独立来源；[live_query_text](../../高炉前端数据/智能助手/backend/qa_task_plan.py:197)只将现场子任务传入查询链。
纯给定数据使用user_message；不查现场、不注入小时分析bundle、不改写数据来源。
“我提供的风温数据……同时查询当前炉顶压力”保留两个任务，查询目标仅为实际alias映射的顶压。
查询时窗、时钟及路由enrichment使用外部子句，原始问题仍保留给最终答复和完成校验。

## 局部与全局约束

| 表述 | 应有行为 |
|---|---|
| 先只用我提供的数据算均值；同时查当前顶压 | 数据分析与独立现场查询均保留 |
| 只用给定数据算均值；再列出我的历史问题 | 保留历史来源，现场查询关闭 |
| 本轮/全程只用提供数据；再查现场 | 全局约束优先，阻止外部来源 |
| 不要调用工具/查询现场数据库 | 明确禁令优先，不能被required工具配置绕过 |
| 我提供了数据；查询这些数据的均值/趋势 | “这些数据”仍指用户输入，不伪装成现场数据 |

r2虽然276项通过，独立审查发现把“只/仅”一律当成全局禁止，错误阻断另行要求的来源。
r3修正scope：局部仅/只遇到独立来源时保留来源；本轮、全程等明确全局范围及原有工具禁令保持优先。
4个旧测试的全局前置条件补为明确“本轮”；追加10例覆盖局部范围、历史/报表、引用范围及全局禁令。r2冻结证据和审查FAIL保留，不改写成通过。
