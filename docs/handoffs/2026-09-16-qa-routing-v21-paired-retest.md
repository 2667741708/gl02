## 4. 新发现的问题与继续复测条件

### ERR-QA-MODEL-ALIAS-DRIFT-20260916 / QAOPT-O01

只读证明`\BlastFurnaceServices\BFOllamaModelSelectionRecovery`计划任务处于启用/运行状态，执行`F:/Ollama/model-switch/manage_ollama_model_switch.ps1 -Action Repair`。其`Activate-Model`在469行对外部业务别名执行`ollama cp`；`Invoke-Repair`在612–627行逐候选恢复，候选失败后尝试下一版本。日志反复记录两个候选的发送请求异常。该程序另外暂停/恢复`BFOllama11434HealthCheck`；这两个任务不是同一个任务，不能只暂停健康任务就认为已禁止自动换模型。

同一`latest`别名因此在下列权重之间往返：

- `:0`：`9111be230d48e53a385a28930fb8cf6972767c83e93c0db51f6b331a534e30fb`，27.8B Qwen。
- `:1`：`e4ad74c41d68de1c8004419d8141a2b2df2275fa08f0dcf326ca0e63fb6d8124`，26.9B Qwen；目录desired_model为此版本。

还观察到tags显示:0而实际驻留ps显示:1。随后二者可恢复一致、8093就绪也可为true，但都不足以证明测试期间稳定。同名不代表同权重；该现象比单纯空闲卸载更严重。两者都是Qwen，问题不是禁止Qwen驻留。

下一步最小受控方案（尚未执行）：

1. 单独授权模型恢复任务维护边界；先查任务状态、运行实例、catalog与active-state，不以故障中临时disabled误判原配置。
2. 暂停`BFOllamaModelSelectionRecovery`自动拉起，等待正在运行的Repair受控完成，再获得已有模型切换互斥锁；不能直接终止而跳过其finally健康任务恢复。Ollama服务保持运行。模型状态变更仅由一个控制者操作。
3. 使用已存在、经核对的模型管理入口固定批准Qwen版本；catalog/public alias/实际驻留digest三者一致，生成探针只发一次。若版本与本轮起始版本不同，单列新模型版本层，不混入固定模型统计。
4. 在测试前/后记录模型digest，防止只在题目前检查遗漏题中切换；故障仅阻断尚未发送题，已有题保留并标版本可验证性。
5. 根据原计划哈希和只读claim审计生成409题续跑计划，保持原题/标准/生产代码哈希；串行每题一POST，无自动重放。5道oracle冲突题单列。
6. 最终逐题独立审核；正确率、完整答复率、传输完成率分别统计，区分知识原文覆盖合同与真实语义正确。
7. finally恢复任务原受控启用状态，检验模型/代理健康、受保护PID及配置哈希。长期修复先保留当前可用模型，再诊断失败；就绪异常不立即反复覆盖公共别名，禁止在活动生成期间切换。

调用管理脚本会影响共享11434，并可能调整健康任务，因此按[AGENTS.md](../../AGENTS.md#L125)“计划任务或其他服务的修改需要单独明确授权和独立验收”，本轮8093授权下未执行以上任务/模型变更。
