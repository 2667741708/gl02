- 状态：模型就绪和知识标准为设计方案；全角色独占已完成本机实现与验证，生产尚未更新。
- 最后核对：2026-09-16。
- 问题：`Q-QA-QWEN-READINESS-CONCURRENCY-ORACLE-20260916`。
- 关联需求：`REQ-QA-FULL-ISSUE-INVENTORY-20260916`；台账QAOPT-O01/O05/T02/T04。
- 权威来源：本轮Reliable SSH身份核验与只读API/配置检查、V20生产代码接缝、冻结知识oracle审计；运行快照不能视作永久配置。

## 1. 先更正诊断与确认Qwen

“模型驻留”指模型已加载到内存/显存，能够减少下一次生成的加载耗时。真正的驻留波动包括被卸载、加载其他模型、runner退出及重启；仅一次HTTP查询失败不能证明这些事件发生。

前轮实际观测为8093健康API的model_ok临时false。当前 `qa_model_readiness.resolve_resident` 将fetch异常替换为空模型列表，最终与批准模型确实不在列表共用ModelUnavailable。因此“模型驻留波动”证据不足，应先改为“模型就绪检查波动，原因待细分”。本轮不得推断已找到卸载根因。

本轮当前只读事实：

- Ollama `/api/ps`：`chiqiongblastfuenace:latest`正在驻留；显存占用23888371072字节。
- `/api/tags`报告该模型family=`qwen35`、parameter_size=`27.8B`、quantization=`Q4_K_M`。现有业务别名实际就是Qwen系列。
- 8093配置 `BF_LLM_MODEL`及`BF_ALLOWED_LOADED_MODELS`都指向该模型；8093 `/api/ollama/status`本次全部健康。
- `latest`与`:0`当前digest相同；`:1`不同。别名相同权重身份与不同模型版本需要分别记录，不能仅凭family相同自动切换。
- 单卡L20，快照总显存46068MiB、已用26694MiB、空闲19058MiB。空闲量是瞬时值，不能据此承诺高并行。

用户“允许Qwen驻留”的要求与当前业务模型相容。主方案允许批准的Qwen保持驻留，不要求每个问题重新加载。若后续加入另一份Qwen版本，先固定其具体标签、digest、上下文与工具合同，不能将任意Qwen权重视为已验收业务模型。

## 2. 模型就绪解决方案：QAOPT-O01

### 2.1 立即修复错误分类

位置：[qa_model_readiness.resolve_resident](../../高炉前端数据/智能助手/backend/qa_model_readiness.py#L22)，以及生产代理 `resolve_upstream_model/handle_ollama_status`（当前密封V20代理；后续候选需重新读取远端，行号TODO-LINES）。

将运行状态拆为：

| 状态 | 证据 | 行为 |
|---|---|---|
| ready | 实际ps成功，批准模型身份匹配 | 可进入模型推理队列 |
| loading | 已授权加载的明确操作正在进行 | 返回准备中与有限等待 |
| not_resident | ps成功且批准模型确实缺席 | 模型任务显示依赖缺失；确定性任务仍可执行 |
| probe_timeout / probe_failed | 查询超时、网络/HTTP异常 | 返回观察未知；不得宣称模型已卸载 |
| runner_failed | 实际runner错误或退出证据 | 保留本轮有效工具事实，停止需要模型的子任务 |
| saturated | 调度容量或排队上限达到 | 返回排队/过载状态，不伪装成模型不存在 |

内部记录脱敏错误类别、耗时、批准身份匹配、观察时间、请求阶段；公开API不输出原始异常、凭据或生产请求内容。短时重复只读GET允许；既有POST永不自动重放。健康缓存可降低查询压力，但只表示last_observed，不能用缓存true冒充实时ready。

### 2.2 把工具任务与模型任务解耦

TaskPlan先判定执行能力，再检查所需依赖：

- 正式原文、目录、明确单点读取和确定性统计，只需对应数据源/执行器健康，不以模型驻留为必要条件。
- 为用户提供的数字求均值等常见任务补确定性解析及计算门，明确可计算时不受模型检查阻断；现有用户数据分析通过不等于已具备独立无模型计算器。解析不清时澄清，复杂推理仍需模型。
- 通用解释、因果分析、复杂语义判断才要求模型就绪。
- 复合任务逐项执行；模型子任务失败保留已完成的数据/知识任务，明确partial和缺项。

当前 `run_qa_failed_retest_once.model_required`对多数非文档题仍保守要求模型，须与真实生产执行能力统一；不能仅改测试器放行来掩盖服务器依赖。

### 2.3 稳定驻留与模型身份

1. 统一8093及已授权其他调用方的业务模型标签与批准digest，减少同权重别名产生的身份误判；不同digest保持版本边界。
2. 先审计各调用方实际keep_alive及是否发送0/卸载操作，当前expires_at快照约一天，不能假定问题由默认5分钟引起。
3. 业务请求统一合理的keep_alive；如采用-1长期保留，需复核当前Ollama版本及调用方覆盖关系，不承诺抵抗重启/显存压力/其他卸载操作。
4. 加载缺席模型只由明确的受控准备操作负责，采用单次启动/单航班；不让多个浏览器或健康GET分别触发加载，不用反复重启服务维持健康。
5. 保持已批准的单加载槽；8093所有角色共用一个活动问答名额，其余发送直接提示使用中，不建立多人问答等待队列。同一获准请求内部的独立只读步骤是否并行，另按工具预算验证。
6. 先观测8093独占门及外部占槽，再决定跨服务协调。跨8094/Ollama配置的变更需要对应独立受控发布；8093进程内独占不能证明其他进程已受同一约束。

Ollama事实依据：[驻留及并发文档](https://docs.ollama.com/faq)、[实际加载模型API](https://docs.ollama.com/api/ps)。keep_alive请求参数覆盖全局设置；并行请求会增加上下文相关内存需求。

### 2.4 可核对验收

- 故障夹具分别覆盖ready、成功空列表、timeout、HTTP失败、坏JSON、非批准模型、同digest批准别名与不同digest、runner失败。
- 成功空列表才归not_resident；观测失败一律unknown/probe_failed，不能统一报未驻留。
- 模型不可用时，明确单点/确定性统计/原文/已支持用户数据计算仍完成；复杂分析只阻断所需子任务。
- 本机负载阶段记录队列等待、首token、全轮耗时、runner重启/加载次数及峰值显存。生产定向测试只发新的已批准轮次，一题一claim，不重跑既有轮次。
- 验收完整答案、来源和完成状态；守卫拒绝后的确定性事实与模型推断分别计分。

## 3. 多角色独占使用解决方案：QAOPT-O05

用户后续明确限定“同一时间只能有一个人使用”。当前实施口径为8093问答请求全局独占：访客、operator/admin以及不同私有会话共用一个生成名额；生成结束或确认停止后释放，其他请求直接返回使用中，不排队或自动重发。浏览页面/只读历史不占用名额，不扩展为整个登录会话锁。

角色能力与owner隔离仍需验收；资源调度改为一个活动请求，取消进行中不能提前释放。本机已实现并通过9项独占生命周期测试，生产尚未更新。不能据此称operator/admin真实生产角色测试通过。[实施证据](2026-09-16-qa-exclusive-use-local.md)。

### 3.1 服务端边界

1. 身份从受控登录会话获取；用户请求不能指定owner或借管理员身份读取其他owner问答。
2. operator/admin私有会话按owner隔离，历史/项目/附件/缓存/取消及状态查询全部执行同一校验。
3. shared guest本来就是同地址共享房间，不能以访客互不可见作为错误验收标准；拒绝访客使用私有项目/路径/附件，8093/8094房间默认仍隔离。
4. 所有问答会话全局仅一个活动请求，防止并行生成和对象交错；其他人返回HTTP409/assistant_in_use，无私有请求ID。共享房间前后相邻用户的指代歧义仍需澄清，明确对象优先，不能因串行而视作同一个用户。
5. 本轮不建立多人推理等待队列；发送被拒绝时保留问题并提示稍后手动发送，不能自动排队、后台重发或让管理员绕过独占门。
6. 登录过期/断线/取消不得自动重发；不持有数据库连接等待模型；不复用跨owner的答案缓存。

### 3.2 测试矩阵及通过条件

| 场景 | 必须证明 |
|---|---|
| 两guest同时发送 | 一请求进入，另一使用中拒绝；按共享合同可见；无自动重发 |
| 两operator不同owner | 一活动请求，另一使用中；历史、来源ID、项目及取消互不越权 |
| operator+admin | 管理员不能绕过全局独占；各自owner隔离 |
| guest+operator+admin | 全角色只有一个活动请求，其余拒绝，不泄露占用者私有ID |
| 同一私有会话双发送 | 不生成交错回合；明确busy或重复请求终态 |
| 一请求取消、其他发送 | 确认停止前仍busy，停止后下一次人工发送可进入 |
| 会话过期/伪造会话ID | 拒绝越权并保留问题供人工重新发送 |
| 慢工具/失败/占用中 | 占用覆盖准备、工具和生成阶段，失败释放名额，无重复POST |

先离线合同与本机2/5/10客户端阶梯测试，再生产小规模受控冒烟。使用已有受控角色会话，缺少夹具记录dependency_blocked，不创建生产账号或改权限补绿。不同新问题各发一次，记录并发开始/终态、所有权检查、工具参数及答案核查；长期pass^k通过独立批准测试轮次获得。

## 4. 知识标准冲突解决方案：QAOPT-T02/T04

冻结审计833题中30题被oracle冲突阻断；这里oracle是题库的标准答案，不能把它与知识库内容矛盾混为一谈。

当前原因标签：重复问句但标准答案不同20项、章节编号冲突9项、父章节/原文路径冲突11项。同一题可有多个标签，总阻断仍是30，不应相加为40题。

### 4.1 每题修正流程

1. 冻结旧case_id、原题哈希、标准答案哈希、题库版本及冲突标签；保留旧报告。
2. 以已批准正式原文为基准，确认制度名称/版本、岗位、完整章节路径、条款或表格范围及原文hash。
3. 同问不同标准：确认是否遗漏岗位/章节限定；需要区分时修正题目，保留两题的独立用途；只有确实同任务同标准才标duplicate_of。
4. 编号错误：逐项核对正式标题与编号，优先修正问题引用；不能通过改评分器忽略编号制造通过。
5. 父路径错误：恢复完整层级及岗位限定，不能依靠相同数字命中别的制度或岗位。
6. 无法从原文唯一裁定，保持needs_domain_review并列出缺少的依据；不让模型生成新标准。
7. 形成带old/new哈希、正式依据、修正理由、独立审查结论的v2修正包；用diff审核，旧题不静默覆盖。
8. 已发送的不确定题不重放。经审查修正后的题使用新版本/新测试轮次，受控单次发送；标准一致性、原文完整覆盖与答案语义各自判定。

### 4.2 验收与803题语义补审

- 每个30项原case_id都有修正/重复/领域待核记录，统计分母保留，无法裁定不称通过。
- 803题目前是原文覆盖与来源合同证据，不能推断完整语义正确。按旧case_id/问题hash逐条对齐旧828待审记录，区分已覆盖/待语义/阻断/新版本，不能以oracle_id不同而丢旧结果。
- 持出语义审查覆盖岗位、短术语、未编号原子条款、完整表格、长章、多章、未知/缺章及跨来源混合；每条核对答案范围与原文，不只找字符串。
- 先纯解析/只读索引验证，再新的生产定向轮次，避免为题库错误消耗模型。

权威审计：[knowledge_oracle_audit_20260916.json](../../tests/qa_regression/knowledge_oracle_audit_20260916.json)，知识覆盖及冲突不能计为同一通过率。
