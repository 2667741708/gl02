1. 在逐题CSV按source_path/category查看来源，按collection_status查看是否已收集，按answer_review_status查看是否已判定。

## 3. 目标架构与统一任务合同

### 3.1 固定执行顺序

授权和能力边界 → 意图/引文分离 → TaskPlan → 既有证据检查 → 补证据执行 → 固定计算 → 事实表与解释 → 覆盖和忠实度校验 → 明确终态。

普通明确请求走确定性解析；复杂歧义用一次受schema约束的规划，输出必须验证。计划不足时澄清，不默认塞进传感器查询。保留批准的当前模型，不因本方案增加第二常驻模型或多智能体。

### 3.2 TaskPlan字段合同（拟新增）

|字段|要求|校验|
|---|---|---|
|task_id / subtask_id|每项用户需求稳定编号|答案段落必须可对应|
|intent|general/document/user_data/context_data/live/history/report/compound|允许混合子任务|
|instruction_spans / quoted_spans|区别真正指令与规程引文|引文中的操作词不得触发动作|
|entities|标准对象、别名、角色、方位完整集合|未知对象不猜ID|
|time_windows / baseline|时区、起止、边界、基线定义|对比不得少窗口|
|document_ref|文档ID、版本、岗位、章节路径|不能只用章节末尾数字|
|evidence_requirements|每个子问题要求的来源、字段、质量和时效|文档不能用聊天替代；目录不能证明实测|
|existing_evidence|可复用证据ID及适用条件|owner、时间、单位、质量均需检查|
|allowed_capabilities / forbidden_capabilities|只读来源、禁止代码/写入、禁止实时查询等|调度器硬约束，Prompt不能覆盖|
|steps / depends_on|查询、计算、解释及依赖|上游失败不猜下游参数|
|budgets|每步超时、总时限、调用与输出预算|不盲目增加工具轮数|
|completion_contract|必须覆盖的对象×窗口×字段×子任务|满足或明确缺项才能终结|

### 3.3 决策表

|优先判定|执行规则|典型反例|
|---|---|---|
|权限与禁用能力|只拒绝不允许的子任务，其余允许部分继续|“分析数据并写脚本”：保留分析，拒绝脚本|
|制度/文档原文|精确文档章节检索，必要时展开正文和表格|引文含“曲线”不画图|
|显式历史问答|当前owner聊天检索|“以前问过顶压吗”不查当前顶压|
|用户数据/既有证据|足够则直接分析，缺项才补证据|用户给定表格不强制查询现场|
|一般知识|直接解释；厂规主张须文档依据|“顶压升高有哪些原因”不强制查实时|
|实时/历史数据|目录解析后查询全部对象与时间窗|南北、A-D、CO/CO2/H2必须展开|
|报表|定位→正文→摘要|目录列表只适用于列报表|
|综合问题|分解并合并共享取数，逐子任务合成|单次工具成功不等于全部完成|

禁止将“工具用了”“有答案”“guard未报错”当作任务完成。路由最终必须同时检查意图匹配和证据覆盖。

## 4. 知识检索、证据与分析的具体合同

### 4.1 文档知识

- 先解析文档/岗位/章节，再检索关键词；保留keyword基线，优先修复索引、章节展开和来源筛选。
- 原文任务检索到标题后必须读取正文；父章节展开指定子章节，表格包含表头、单位、注释和合并单元格语义。
- 全章过长可以有结构地分段回答，明确范围；不能把“部分片段”写成“全部规定”。
- 规程版本冲突时给版本差异或请求指定版本，不自行混合条款。
- 聊天、测试记录、模型旧答案不属于原文证据。显式需要报表对照时可并列引用，但不能替代规程。

### 4.2 EvidenceLedger

每条事实保存：evidence_id、类型、对象、字段、值、单位、观测/有效时间、窗口、质量、来源及权限；计算结果另保存输入ID、公式和计算器版本。请求成功事实的生命周期长于工具连接。

证据状态分为可用、缺失、过期、低质量、冲突、禁止使用。确定性事实段先生成，模型只生成解释段。最终校验绑定对象和字段，支持声明的舍入与换算，不对全文做粗糙数字集合匹配。

### 4.3 综合分析深度

例如“三个指标两段时间对比并结合规程解释”，先列六项取数需求，再做时间/单位/缺失检查，固定计算差异，检索相应条款，最后回答每项子问题。输出应包含：

1. 能成立的直接结论。
2. 支撑结论的数据/条款及时间范围。
3. 合理解释及其假设，明确相关性与因果的区别。
4. 冲突、缺项、过期数据和结论限制。
5. 还需核查的最少信息；不擅自写入生产设定。

## 5. Prompt补全方案

### 5.1 统一基础目标（拟替换为共用版本）

> 你是面向高炉业务的智能助手，帮助用户完成一般问答、工艺知识解释、正式规程检索、只读数据查询和基于证据的分析判断。
>
> 先理解用户要完成的任务，并区分用户指令、引用内容和已有数据。信息足够时直接回答；只有缺少必要证据时才使用允许的工具。不得为了展示工具能力而查询无关数据。
>
> 综合问题逐项处理全部对象、时间范围和子问题。区分正式文档原文、用户给定数据、实时实测、历史记录与推断。不得编造数值、来源、章节、时间或能力。
>
> 原文题引用批准版本的文档正文；无法取得原文时明确缺项，不能用一般知识补写规定。历史问答仅在用户要求回忆时检索，不将聊天记录当权威知识。
>
> 允许数学、统计和基于数据的条件性判断；复杂计算使用批准的固定计算功能。禁止生成代码示例、脚本、SQL或命令，也不执行代码。禁止自动修改生产设定。
>
> 工具失败时保留已有有效事实，说明失败影响范围；证据不足时澄清或给有边界的部分回答。不要把无关现场快照插入知识答案。
>
> 先给结论，再给依据与必要限制。篇幅以完成用户要求为准，不因固定短字数丢失必答项。

### 5.2 分支附加合同

- document：原文位置、版本、章节覆盖、引用校验。
- data：对象、值、单位、时间、来源、质量及缺项。
- analysis：输入、计算定义、结果、推断边界与反证。
- history：owner范围、记录时间、避免混同本次测试。
- report：报告业务日期、正文片段与总结。
- degraded：成功事实、失败步骤、不能确认的部分；仍遵守一次无工具最终回合上限。

实际能力由注册表提供，不在多个Prompt复制互相矛盾的能力描述。每次发布记录基础Prompt和分支合同版本，13个系统模板逐一绑定入口验证。

## 6. 异常和终态处理

|情况|必须保留/返回|禁止行为|
|---|---|---|
|部分工具成功|成功事实+具体失败子任务|清空为“数据库失败”|
|工具全部失败|声明未核实，给可支持的一般解释或缺项|编造实时值；反复无工具生成|
|模型不可用|可确定的数据/目录/已有证据；需解释部分标未完成|所有路径被模型驻留门禁一并阻断|
|原文缺正文|文档定位情况和缺失范围|补写正式条款|
|用户取消/连接中断|持久化请求与阶段状态，未知发送隔离|自动重发SSE|
|超时/错误参数|准确区分工具/服务/阶段，限制影响面|无差别增加调用轮数|
|权限不足/代码子请求|说明受限部分，允许部分继续|放宽owner、Origin或代码能力|

请求终态使用complete/partial/needs_clarification/restricted/failed/interrupted_unknown。页面状态、日志和评测记录一致。降级是明确的功能结果，不等于所有回答都正确；内容仍需审核。

## 11. 完成定义

“收集完成”“审阅冻结”“本机修复完成”“候选回归通过”“生产部署完成”是五个独立里程碑。每一步都必须有对应证据，不能由上一阶段自动推定下一阶段完成。任意自然语言问题无法保证百分之百正确；目标是支持范围内可靠完成，证据不足时准确澄清或给出明确部分答案，失败可定位并能进入回归。
