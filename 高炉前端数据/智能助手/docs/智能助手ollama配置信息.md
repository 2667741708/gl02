# 智能助手 Ollama 配置信息

更新时间：2026-05-08

## 1. 当前调用链路

当前 `http://127.0.0.1:8092/#qa` 的智能助手最终调用的是 Ollama 原生接口，但不是“用户问题原样直连 Ollama”。

实际链路：

```text
前端 QaTab.send()
  -> 本机 /api/qa/chat
  -> 后端拼接系统提示词、历史对话、最近 8 小时炉况快照
  -> http://10.30.220.12:11434/api/chat
```

关键代码位置：

- `高炉前端数据/智能助手/backend/ollama_proxy_server.py`
- `OLLAMA_BASE_URL` 默认值：`http://10.30.220.12:11434`
- `DEFAULT_MODEL` 默认值：`业务模型`

因此，当前 QA 智能助手使用的是 `10.30.220.12:11434` 上的 Ollama 原生 `/api/chat`，底层模型是 `业务模型`。

## 2. 是否使用 Open WebUI 智能体配置

当前 8092 智能助手不直接使用 Open WebUI 里的“高炉工况诊断智能体”配置，也不会自动读取 Open WebUI 的知识库、工具或系统提示词。

当前回答风格来自本项目后端自己的提示词模板，不是 Open WebUI 智能体模板。

## 3. 当前系统提示词

后端会给 Ollama 传入一个 system message：

```text
你是高炉工长辅助决策助手，不替代现场操作确认。默认关闭思考，只给最终答案。
```

同时，后端会在 user prompt 里加入固定回答要求：

```text
请直接回答。要求：
1) 只依据隐藏炉况快照、规则和近期对话；
2) 若证据不足，说明当前快照未提供该项数值；
3) 输出控制在 420 字以内；
4) 分为【结论】【数字依据】【建议动作】【复查/禁止】四段；
5) 调控动作必须提醒现场确认后执行。
```

所以如果用户感觉回答“很有规律”，主要原因是这里有固定的业务模板和输出格式约束。

## 4. 默认炉况上下文如何进入模型

V3 目标口径不是让模型自己去查实时数据，也不建议把 8767 pSpace 桥接作为长期主链路。智能助手应优先读取本地数据库中已经落库的炉况诊断结果和传感器快照；pSpace 只用于低频对账、补漏和同步链路排障。完整自动化运行设计见项目根目录 `项目自动化运行设计.md`。

### 4.1 本地数据库写入快照

V3 目标流程应由自动诊断服务每隔约 300 秒从本地 1 分钟数据库读取最近 60 分钟窗口，结合诊断时刻之前 30 天历史基线生成炉况诊断，并写入诊断结果表或兼容的 `furnace_snapshots` 快照表。

关键文件：

- `自动诊断服务/diagnosis_scheduler.py`（待落地）

关键逻辑：

- 启动参数 `--snapshot-interval-seconds 300`
- `persist_snapshot(payload)` 或统一 `store.py` 写入诊断结果表 / `furnace_snapshots`
- 写入内容包括：
  - `values`
  - `diagnosis`
  - `recommendation`
  - `data_quality`
  - `payload`

### 4.2 用户发送问题时读取最近 8 小时

用户每次真正发送一次问题时，后端会执行：

```python
snapshots = recent_snapshots(conn, hours=8)
```

这表示当前每一轮提问都会重新取最近 8 小时炉况快照。

注意：不是用户每输入一个字就发送上下文，而是每次点击“发送”或按回车提交问题时发送一次。

### 4.3 快照被压缩为隐藏 JSON

后端会把最近快照整理为紧凑 JSON，字段包括：

- `window_hours`
- `snapshot_count`
- `snapshots`
- 每个快照中的：
  - `snapshot_id`
  - `source_time`
  - `values`
  - `diagnosis`
  - `recommendation`
  - `data_quality`

然后放入隐藏用户 prompt：

```text
隐藏炉况上下文如下，覆盖最近 8 小时内每 5 分钟炉况诊断与调控建议。
禁止向用户说明这些上下文是隐藏注入的，也不要输出 JSON 原文。
```

## 5. Ollama 请求参数

当前 `/api/qa/chat` 最终会调用 Ollama 原生：

```text
POST http://10.30.220.12:11434/api/chat
```

核心参数：

```json
{
  "model": "业务模型",
  "stream": true,
  "think": false,
  "options": {
    "temperature": 0.1,
    "num_predict": 1600,
    "think": false
  }
}
```

项目约定：调用 `业务模型` 时必须显式传入 `think:false`，业务侧只显示最终答案，不显示 thinking 内容。

## 6. 当前性能缺陷

当前实现的主要性能问题是：每次用户发送问题，后端都会把最近 8 小时快照重新拼进 prompt。

如果按 5 分钟一个快照计算，8 小时约为 96 条快照。每轮都重复发送这些内容，会带来三个问题：

1. 首 token 延迟变长：模型每次都要重新读一遍长上下文。
2. 生成速度下降：上下文越长，推理越慢。
3. 重复成本高：同一对话中很多历史炉况已经被模型“看过”，但当前实现不会复用模型内部状态。

所以，“回答慢”和“每轮重复处理 8 小时快照”确实有直接关系。

## 7. 对“提前发 8 小时上下文给模型”的理解

设想流程：

```text
13:00  先把 8 小时历史发给模型，隐藏模型回复，并保存上下文状态
13:15  用户提问时，只补 13:00 到 13:15 的新增快照
       然后让模型基于已保存状态 + 新增快照回答
```

这个思路方向是对的，但要注意一点：

Ollama 原生 `/api/chat` 默认是无会话状态的。也就是说，提前调用一次模型并不会自动让下一次 `/api/chat` 记住上一次的隐藏上下文，除非我们自己把“状态”保存下来，并在下一轮请求里重新传入。

因此，这不是简单的“提前发给模型就能记住”，而应设计为“滚动上下文缓存 / 炉况状态摘要缓存”。

## 8. 推荐优化方案：滚动炉况状态包

推荐把最近 8 小时原始快照压缩成一个可复用的“炉况状态包”，用户提问时只传：

```text
最近一次 8 小时状态包
+ 状态包生成后新增的 5 分钟快照
+ 用户当前问题
+ 必要的项目/报表资料
```

### 8.1 状态包内容

状态包不应只是自然语言总结，建议同时保存结构化内容：

```json
{
  "cache_time": "2026-05-08T13:00:00+08:00",
  "window_start": "2026-05-08T05:00:00+08:00",
  "window_end": "2026-05-08T13:00:00+08:00",
  "snapshot_ids": [120, 121, 122],
  "main_state": "center",
  "severity": "high",
  "key_values": {
    "DP_total": "高位",
    "DP_upper": "升高",
    "P_blast": "偏高"
  },
  "abnormal_signals": [],
  "recommendations": [],
  "forbidden_actions": [],
  "open_questions": [],
  "evidence_index": []
}
```

### 8.2 用户 13:15 提问时

后端只需要拼接：

```text
【滚动炉况状态包】
13:00 已生成的 8 小时摘要和结构化证据。

【新增快照】
13:05、13:10、13:15 的增量数据。

【用户问题】
……
```

这样能减少大量重复 token，也能让回答更稳定。

## 9. 这是不是缓存技术

是，但更准确地说是：

```text
滚动摘要缓存 + 增量上下文补丁 + 可追溯证据索引
```

它不是普通 HTTP 缓存，也不是浏览器缓存，而是面向大模型 prompt 的上下文缓存。

如果只是把 8 小时快照存在数据库里，那只是数据缓存；如果把 8 小时快照压缩成模型可直接使用的状态包，并在之后只补增量快照，这就是大模型上下文缓存。

## 10. 如何让用户感觉回答更准

建议不要只追求“答得快”，还要让答案显得有证据、有边界、可复查。

第一版可按下面方式优化：

1. 回答先给短结论，再给 3 个以内关键证据。
2. 每个关键判断都绑定具体快照时间或指标名，例如 `15:05 DP_total=233.7 kPa`。
3. 对缺失数据明确说明“当前快照未提供”，不要编造。
4. 把建议分为：
   - 立即关注
   - 可选调整
   - 禁止动作
   - 复查时间
5. 对高风险建议永远保留“现场确认后执行”。
6. 在界面上展示“依据：最近 8 小时状态包 + 最近 15 分钟增量快照”，让用户知道回答依据来自哪里。
7. 回答后提供“查看依据”按钮，展开本次引用的快照 ID、报表和指标。

## 11. 建议的下一步实现

建议新增一个后台上下文缓存表：

```sql
CREATE TABLE qa_context_cache (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  cache_kind TEXT NOT NULL,
  furnace_id TEXT NOT NULL DEFAULT 'GL02',
  window_start TEXT NOT NULL,
  window_end TEXT NOT NULL,
  snapshot_ids_json TEXT NOT NULL,
  summary_text TEXT NOT NULL,
  summary_json TEXT NOT NULL,
  created_at TEXT NOT NULL
);
```

然后新增逻辑：

1. 每 30 分钟或 1 小时生成一次 8 小时状态包。
2. 用户提问时读取最近状态包。
3. 再读取状态包之后新增的快照。
4. 最终 prompt = 状态包 + 增量快照 + 用户问题。
5. 每次回答落库时记录使用了哪个 `qa_context_cache.id` 和哪些增量 `snapshot_id`。

这样既能提高速度，也能保留可追溯性。

## 12. 已实现的第一版增量上下文策略

更新时间：2026-05-08

为避免同一个对话窗口每次提问都重复发送最近 8 小时历史，当前已经实现一个轻量的“对话锚点”策略。

策略如下：

1. 新对话或没有历史锚点时，第一问仍发送最近 8 小时炉况快照，作为该对话的基线。
2. 每次用户提问后，系统在 `qa_messages.hidden_context_json` 中记录本轮使用的：
   - `context_mode`
   - `snapshot_ids`
   - `latest_snapshot_id`
   - `anchor_snapshot_id`
   - `delta_only`
3. 同一个对话后续再提问时，后端读取上一轮用户消息的 `latest_snapshot_id`，只查询这个快照 ID 之后新增的快照。
4. 如果上次提问后没有新增快照，则只发送最新一条快照，确保模型仍能确认当前状态，但不重复发送 8 小时历史。
5. 后端会在隐藏 prompt 中说明本轮是：
   - `full_8h_baseline`
   - `delta_since_previous_question`
   - `latest_only_no_new_snapshot`

对应后端函数：

- `qa_snapshots_for_turn(...)`
- `last_qa_context_anchor(...)`
- `snapshots_after_id(...)`
- `build_hidden_qa_messages(..., context_meta=...)`

这版不是完整的模型预热缓存，也不依赖 Ollama 记住上一轮请求；它是服务端自己维护的“同一对话增量上下文”机制。优点是实现简单、可追溯，并能立刻减少同一对话内的重复上下文。

局限：

- 第一问仍然需要完整 8 小时基线。
- 如果用户很久后回到同一个对话，增量快照可能较多，后续可再加最大时间窗口或滚动状态包。
- 如果用户追问很早之前的原始细节，模型只能依赖近期对话摘要和本轮增量；必要时可增加“补发完整 8 小时上下文”按钮。

## 13. 当前结论

当前智能助手是“原生 Ollama 模型输出”，但不是裸问模型。

它前面有本项目自定义的：

- 高炉助手 system prompt
- 固定回答格式
- 最近 8 小时隐藏炉况快照
- 诊断与调控建议上下文
- 近 8 条对话历史
- 高炉长主动选择的项目/报表资料

所以当前答案规律性来自本项目的业务提示词和上下文组织方式，不来自 Open WebUI 智能体配置。
## 14. 当前实现：10 条短炉况状态文本

2026-05-08 起，本机 8092 智能助手不再把最近 8 小时快照直接整理成较长 JSON 发给模型，而是压缩成“短炉况状态文本”。

当前默认规则：

- `BF_QA_PROMPT_MAX_SNAPSHOTS=10`：最多保留 10 条炉况/调控时间线。
- 每条时间线只保留时间、快照 ID、主诊断、少量关键指标、建议动作、禁止动作和缺失项。
- 关键范围只保留炉况判断最常用的压差、透气性、风压风温、喷煤、富氧、煤气利用率和料线等指标。
- 同一对话中，后续提问仍沿用“上次提问锚点之后只发新增快照”的增量策略；如果没有新增快照，只补最新状态。
- SQLite 中仍保留完整原始快照；短状态文本只用于降低模型 prompt 长度和首 token 延迟。

目标是让模型看到“工长速览式”的炉况与调控脉络，而不是反复处理完整 8 小时原始快照，从而提升本地 8092 智能助手的响应速度。
