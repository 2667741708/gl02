# 四类核心测评合同

## 1. 传感器证据落地推断

用户若称“传感器证据落地判推断”，按本类同义处理；规范名称为“传感器证据落地推断”。

验证链路：自然语言对象 → 标准点位 → 只读传感器工具 → 带时间/来源的证据 → 有边界的模型推断。

必须检查：

- 实际点位 ID 与用户语义一致；不得用相似点位替代。
- 至少保留值、单位、数据时间、质量和来源；缺失字段必须明示。
- 单点只能支持当前状态描述，趋势推断必须有明确时间窗和足够样本。
- 模型须区分“数据事实”“合理推测”“证据不足”，不得把推测写成已确认事实。

## 2. 确定性工具增强计算

统计、聚合、相关性、公式运算优先由数据库、MCP 或受控计算器确定性执行；模型只解释结果。

必须检查：

- 明确总体/样本标准差、时间窗、样本数和缺失处理。
- 答案列出公式、输入值、单位和结果。
- 至少独立复算一个关键结果；误差不超过 `1e-6` 或已声明的业务容差。
- 工具已返回用户要求字段而答案遗漏时，答案合同判失败。

## 3. 多工具跨 MCP 编排

验证同服务批量、多轮依赖、跨服务并行 DAG 和进一步计算工具，不把“工具数量多”误写成“跨 MCP”。

必须检查：

- 报告实际 `server_id/tool/arguments/step_id/depends_on/elapsed_ms`。
- 无依赖且不同服务的步骤可并行；同一 stdio 服务或有依赖步骤按合同串行。
- 依赖步骤只能消费已验证的上游输出；不得由模型猜参数。
- 部分失败保留成功事实并明确缺口；全失败只允许一次无工具降级回答。

## 4. 最终答案证据忠实度评估

这是所有真实工具用例的最终门禁，独立于 MCP 是否成功。

逐项核对：

- 用户要求的值、单位、时间戳、来源、样本数、公式和限制条件是否齐全。
- 答案数值能否在工具结果中定位，或由已列公式独立复算得到。
- 是否把旧数据写成当前数据、把缺失写成 0、把相关性写成因果、把工具错误隐藏成正常。
- 工具轨迹、答案与报告是否共享同一 `case_id`，便于审计和复现。

建议状态：`passed / failed / not_applicable / not_tested`。任何未核实实时数值、跨 owner 泄露、
未授权写入或错误自动重放均为阻断项。
