# GL02 数据同步守护任务说明

本任务用于守护 220.12 本地 PostgreSQL 中的 `bf_sensor.one_minute_values` 数据同步。

## 目标

- 定期确认 `sync_from_243_pg.py --continuous` 是否仍在运行。
- 定期确认 PostgreSQL 最新 `ts` 是否滞后当前时间。
- 若同步进程失活或数据滞后，先清理残留失败进程，再重新启动实时同步。
- 扫描最近 12 小时的分钟级空洞，自动用 `--start-time/--end-time` 从 243 回补。
- 扫描最近 90 天的小时级全空洞，按小批量自动从 243 回补。

## 入口

```powershell
数据库同步和存取\run_sync_watchdog.ps1
```

内部调用：

```powershell
python src\sync_watchdog.py
```

## 推荐计划任务

任务名：

```text
\GL02SensorSync\Watchdog
```

推荐频率：每 5 分钟运行一次。

## 日志

- `logs\sync_watchdog_runner_YYYYMMDD.log`
- `logs\sync_watchdog_YYYYMMDD.jsonl`
- `logs\sync_watchdog_state.json`

`sync_watchdog_state.json` 保存最近一次检查结果，包含：

- PostgreSQL 当前数据范围。
- 实时同步进程列表。
- 是否触发重启。
- 最近 12 小时空洞。
- 最近 90 天小时级空洞。
- 自动回补范围和结果。

## 保护策略

- 单次最多回补 3 个时间段。
- 单次最多回补 1 小时。
- 回补使用 `batch-size=4`、`max-workers=1`，避免对 243 pSpace 造成压力。
- 使用 lock 文件防止 watchdog 重入；锁超过 30 分钟会被视为陈旧锁并清理。
- `run_realtime_sync_pg_bg.ps1` 当前默认每 30 秒轮询一次最近 10 分钟数据。
- 默认同步源为 `--source-mode raw --source-aggregate sample --target-aggregate PS_RAW_SAMPLE`：先读取 pSpace `HisReadRaw` 约 5 秒原始样本，再为每分钟选择最后一个有效 raw 值写入 `bf_sensor.one_minute_values`。
- `run_sync_watchdog.ps1` 当前使用 `--stale-minutes 6`，当 220.12 本地 PostgreSQL 最新数据滞后约 6 分钟或实时同步进程异常时，会更早触发重启和小窗口补漏。
- Watchdog 默认只处理近实时/近期缺口，使用 raw sample 写每分钟一行，避免历史大窗口补漏阻塞实时同步。
- 90 天历史小时级空洞只在显式传 `--history-backfill-enabled` 时处理，并强制 `--source-mode processed`，避免用 5 秒 raw 做大窗口回填。
- 当前主链路仍只保存每分钟一行；raw sample 模式只改变读取源和分钟采样口径，不把 5 秒 raw 明细直接写入 `bf_sensor.one_minute_values`。如需保留 5 秒明细，应另建 raw/real-time 表。

## 近实时守护修改清单

排查“数据库时间不够实时”时，先确认是哪一段延迟：

- 220.12 生产延迟：在 220.12 本机 PostgreSQL 查询 `bf_sensor.one_minute_values.max(ts)` 与 `localtimestamp` 的差值，含义是 `243 pSpace/数采 -> 220.12 PostgreSQL`。
- 本地镜像延迟：比较本地 Docker PostgreSQL `127.0.0.1:15432` 与 220.12 的 `max(ts)`，含义是 `220.12 PostgreSQL -> 本地 Docker/8092`。

2026-05-14 已验证的守护修复路径：

- `run_realtime_sync_pg_bg.ps1`：读取结束时间必须用当前 `Get-Date`，不要用 `Get-Date.AddMinutes(-1)`；否则 30 秒轮询加分钟落桶会自然形成约 2-3 分钟延迟。
- `run_realtime_sync_pg_bg.ps1`：默认参数为 `PollSeconds=30`、`LookbackMinutes=10`、`SourceMode=raw`、`SourceAggregate=sample`，目标聚合标记为 `PS_RAW_SAMPLE`。进一步压延迟时，先试 `PollSeconds=10-15`、`LookbackMinutes=3-5`，并看 pSpace 压力和 `tags_error`。
- `src/sync_watchdog.py`：判断实时同步是否存在时，只能把命令行匹配 `-File ...run_realtime_sync_pg_bg.ps1` 的进程当作真实实时外壳，并排除 Watchdog 自身；不能把 `powershell -Command` 进程误判为实时同步。
- `src/sync_from_243_pg.py` 与最新日志：每轮必须能看到 `source_mode=raw`、`source_aggregate=sample`、`target_aggregate=PS_RAW_SAMPLE`、`tags_ok=115`、`tags_error=0`。
- `config/sync_config.json`：默认值必须与守护入口一致，防止零值审计、文档和实际同步口径分裂。

守护重启原则：优先触发 `\GL02SensorSync\Watchdog`，由 Watchdog 清理异常进程并拉起实时同步；旧 `\GL02SensorSync\Realtime` 应保持禁用，避免两个 continuous 进程同时打 243 pSpace。若需要手动重启，先确认没有另一个真实 `run_realtime_sync_pg_bg.ps1` 常驻，再启动守护。

验收 SQL：

```sql
SELECT
  max(ts) AS max_ts,
  localtimestamp AS db_now,
  round(extract(epoch FROM (localtimestamp - max(ts)))::numeric / 60, 3) AS lag_min,
  count(DISTINCT tag_long_name) FILTER (
    WHERE ts >= (SELECT max(ts) - interval '10 minutes' FROM bf_sensor.one_minute_values)
  ) AS tags_latest_10m
FROM bf_sensor.one_minute_values;
```

合格信号：`lag_min` 稳定约 1-2，`tags_latest_10m=115`，最近 `bf_sensor.sync_runs.tags_error=0`，`logs\sync_watchdog_state.json` 中存在真实 realtime shell PID。`Watchdog` 计划任务最近结果为 `0` 只代表任务进程正常结束，不代表数据完整。
